# Dashboard: backend capabilities worth bringing into the frontend

**Date:** 27 October 2026  
**Status:** EXTRA C0 SOURCE AUDIT / recommendation only; no product code or new acceptance claim.  
**Owner:** AI-Verse-System, linked to [the reuse-only composition plan](LOCAL-FIRST-DESKTOP-FULL-OS-COMPOSITION-2026-10-27.md) and [System PR #297](https://github.com/aiverse-filmmakers/AI-Verse-System/pull/297).  
**Main implementation owner:** [AI-Verse-Dashboard PR #42](https://github.com/aiverse-filmmakers/AI-Verse-Dashboard/pull/42) after MC2.1/Personal-first plan review.  
**Request:** Audit what the already-built backend can do that the current Dashboard does not expose, make useful capabilities visible without overwhelming the user, and **do not rebuild or modify** Distribution, OS, Brain, Memory, Skills or Data. Reuse other completed components through existing contracts. Connections feature expansion remains out of the initial critical path.

## 1. Executive decision

**Build a contextual product UI over the existing owners, not a repository-by-repository admin console.** The Dashboard should feel like a normal calm workspace with chat, a selected context, and a place to see current work. Only surface more controls when a user needs to act. Capabilities may be operationally complete behind the scenes but still absent from the Personal preview.

**Highest-value gaps:** real Chat/Run progress; one consolidated Needs Attention/Approvals queue; live Bots and temporary Worker activity; Brain Goals and objective evidence; Automation schedule/heartbeat status; usage/cost truth; Skills and Memory visibility; a useful workspace-specific Data view; system service health and recovery. These have actual backend owners and usually existing read/query methods. The first missing piece is still a trusted Dashboard-hosted, authenticated, scope-bound integration route.

**Avoid:** always-visible seven-panel monitor, duplicate databases and notification stores, fabricated Agent/Bot status, pretending a listed model is connected, showing opaque subsystem names by default, unrestricted transcript/memory inspection, new provider OAuth/paid requests, editing protected Core, or treating aspirational Apps/film tools as shipped runtime.

## 3. One simple UI, not fourteen backend dashboards

Use the already-built **Personal shell**; keep chat present and respect existing split/resize/focus parity. The following is a **navigation model**, not a redesign brief:

| Surface | Ordinary resting UI | Contextual reveals | Advanced on demand |
| --- | --- | --- | --- |
| **Top bar** | Personal / Filmmaking, active workspace, subtle connection state, *attention count only if >0* | Switch OS/workspace; Needs Attention list; true service status | Full doctor, multiple systems, security |
| **Chat** | All chat panes same real owner-backed composer; one small current-run indicator | @ real Bots/teams, Skills chooser, active goal/context reference, legal Stop/Approve/Retry | Run events, scope/provenance, budget/diagnostics |
| **Existing Teams popover** | Hidden until requested | Real Bot roster, roles and task count; current Task/Team Run details, plan-before-create | Owner-legal lifecycle, team templates, Rooms, advanced execution |
| **Existing app picker** | Canvas, Notes, References, Activity (keep these starting surfaces) | Activity combines owner-sourced work and attention; offer Data only for a workspace where available | Structured Data/analytics and raw logs as separate optional app |
| **Personal/Work context** | Active goal or next meaningful task only when one exists | Goal status/evidence, scheduling and task detail | Full Brain strategy/learning plan |
| **Settings** | Basic Connection, AI/provider, Usage, Skills/Knowledge, Scheduled work, Installation | Read-only statuses and owner-verified actions | Cost provenance, Skill Workshop, Memory source audit, doctor/recovery, channels |

**Progressive disclosure rules:**

1. Never mount empty cards for every owner on initial launch. “Nothing requires your attention” is enough when the system is healthy; no dashboard wallpaper.
2. One **Needs Attention** count, not separate approval alerts from Bots, Gateway and Automations. Source-identify each row, dedupe by canonical owner identity and event ID, and preserve each owner's actual approval boundary. Derived read/unread cursor is UI metadata, not a notification store.
3. An AI tool/model/skill is a selectable action only after backend presence, capability, runtime and permission discovery pass. Unsupported options must be truthfully unavailable. A green component doctor is not execution authorization.
4. When a user asks “what did you do?” answer from existing run/task/wake/evidence receipts, not a fabricated activity feed or hidden chain of thought.
5. Learning and internal organization normally need no new modal. Surface meaningful mistakes and corrections as contextual “Review/Undo” rather than flooding the user with system internals.
6. Keep names human: “Your team”, “Work in progress”, “Needs your decision”, “Scheduled work”, “What AI remembers”, “Usage” and “Health”. Allow raw Brain/Gateway/Token labels only in developer details.
7. Two-system A→B→A, workspace changes, chat pane targeting and late streams must not leak selected tasks, approvals, Memory, spend, files or action authority.
8. All native/file/secret interactions occur at the trusted host or canonical owner, never inside the GitHub Pages design preview.

## 5. Implementation decisions and next step

**Decision D1:** Make only the high-frequency, safety-critical surfaces default: Chat, current workspace, Activity when work exists, and Needs Attention when action is required. Nothing else should be permanently occupying visual space.

**Decision D2:** The strongest next missing features are **not** a new workflow designer or the entire technical Control Center. They are **owner-backed attention/approval, real agent roster and Task/Team Run projection, Goals, scheduled work, real Skills and Memory visibility, and Token evidence**. The backend already provides most underlying semantics, so each belongs to existing Dashboard integration slices.

**Decision D3:** Keep first-release features conditional on the exact installed component profile. **Core-only users should still have their existing excellent Codex/IDE Core unchanged**; optional Agent/Full components and their UI must not be forced onto them. A hidden or disabled feature is preferable to silently installing/upgrading owners.

**Decision D4:** No auto-enabling future effects. Creating permanent Bots, scheduling recurring work, connecting external accounts, requesting new permissions, and consequential paid/destructive operations require existing explicit approval/grant. Safe reversible internal context organization should remain primarily invisible.

**Decision D5:** Prioritize real data correctness over UI coverage. A pane filled with simulated task status or "0 cost" in place of UNKNOWN is worse than a clearly unavailable tool.

**Decision D6:** Maintain one engineering tracker: System [C0-C6 integration plan](LOCAL-FIRST-DESKTOP-FULL-OS-COMPOSITION-2026-10-27.md) coordinates product-level acceptance; Dashboard keeps its existing MC2/PRD/quality tracker, accepted 15/100 and actual code. This audit merely adds capability-to-UI mapping, not a new 20-slice backlog. Formal protected Dashboard amendment and C0 acceptance remain pending review.

**Next action:** Use this shortlist to tighten the **existing MC2.1 typed Gateway/owner facade design**, so new Chat doesn't become a dead end. Implement **C1 authentic Chat first**, then expose P0 attention/activity and the smallest P1 owner-backed tools as their C2-C5 scopes mature. Maintain UI parity and owner proof; do not design a new general dashboard.

**Evidence boundary:** Source-read this turn only; no interaction/user study, actual Mac-installed component inspection or composed runtime/real provider calls. Readmes describe source intent and accepted owner scope but do not themselves prove current private installation or host adapter readiness.
