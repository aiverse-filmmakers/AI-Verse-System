## 3. Gateway run/session/event state machine

Gateway owns canonical runtime-edge state for:

- session binding;
- runs;
- messages;
- run events;
- checkpoints;
- approval state;
- control state;
- idempotency records.

Current run states include:

- queued;
- running;
- awaiting_approval;
- resuming;
- paused;
- parked;
- paused_no_progress;
- paused_recovery_required;
- blocked;
- budget_limited;
- failed;
- canceled;
- completed.

Runtime providers do not become canonical run owners.

## 4. Gateway execution loop

Normal Gateway flow is:

1. authenticated principal creates/resumes a session/run;
2. run binds system/workspace/principal;
3. current owner context is assembled;
4. runtime receives only:
   - bounded context read tool;
   - bounded action tool;
5. runtime output is validated;
6. trusted scope/provenance/authority is derived by Gateway;
7. side effects pass OS authorization;
8. approval pauses when required;
9. approved action is reauthorized;
10. owner action executes;
11. outcome/event is persisted in Gateway run state.

Runtime/model output cannot directly manufacture:

- consent;
- approval;
- trusted scope;
- durable Bot/Automation IDs;
- owner receipts;
- credential authority.

## 5. Goal/Brain continuation

Gateway Goal continuation binds:

- Goal ID;
- Goal version;
- activation epoch.

Each autonomous turn:

1. reads exact owner Goal;
2. executes bounded work;
3. collects evidence;
4. asks Brain Goal owner for evaluation;
5. re-reads exact binding before another turn.

Changed binding revokes continuation.

Brain itself uses:

- explicit Goal mutation receipts;
- optimistic versions;
- evidence-bound completion;
- no-progress/stall budgets;
- deterministic evaluation floors.

Model inference cannot alone satisfy stronger completion criteria.

The existing Brain Goal operation-ID concurrency defect remains `WSA-2026-010`.

## 6. No-progress / parking behavior

Gateway does not self-expand indefinitely.

Current behavior includes:

- configured turn limits;
- budget intersections;
- no-progress threshold;
- parked/paused_no_progress outcomes;
- changed Goal lease revocation;
- explicit resume rather than invisible continuation.

Brain likewise blocks/stalls when completion evidence or progress is insufficient rather than expanding authority.

No new no-progress defect was found.

## 7. Approval flow

Gateway approval state is owner-bound and authenticated.

Normal path:

1. OS returns approval-required.
2. Gateway persists awaiting-approval checkpoint.
3. model/runtime cannot approve itself.
4. authenticated principal must own the run.
5. approval operation is recorded.
6. Gateway re-runs OS authorization.
7. if approval is still required/denied, effect remains blocked.
8. owner action executes only after the late check.

Multiple Bots has a separate coordination Approval lifecycle for Bot/Task execution.

Automation-ingressed Bot work preserves that normal approval gate and does not enqueue the Task until approval succeeds.

The Multiple Bots operator identity defect remains `WSA-2026-022`.

## 8. Pause, cancel and resume

Gateway exposes authenticated:

- pause;
- cancel;
- resume;
- approval controls.

Sequential behavior is correct.

However, current execution/control transitions are not linearizable.

A stale run object held by asynchronous execution can overwrite a newer persisted pause/cancel state.

This can allow:

- canceled/paused state to disappear;
- post-cancel continuation;
- later owner/background work after the operator believed the run was stopped.

This remains existing HIGH finding:

`WSA-2026-008`.

No duplicate finding is opened.

## 9. Gateway run/retry idempotency

Sequential idempotency correctly binds key to payload and rejects changed reuse.

Concurrent first claim is not serialized.

Two simultaneous first claims can both observe no reservation and both become new runs.

This affects:

- client run retry;
- Automation wake replay;
- session first binding;
- privileged control transition races.

Again this is existing `WSA-2026-008`.

## 10. Automations occurrence identity

Automations has strong canonical occurrence identity.

Scheduled occurrence identity derives from:

`automation_id + trigger_id + exact scheduled instant`

Event/webhook occurrence identity derives from:

`automation_id + trigger_id + stable source event ID`

The store enforces invocation ID uniqueness.

Trigger claim + advancement occur in one SQLite `BEGIN IMMEDIATE` transaction.

Concurrent scheduler ticks therefore converge on one canonical occurrence.

Definition/trigger versions act as execution kill fences after pause/edit/archive.

## 11. Automations retry/recovery

Every delivery retry:

- re-enters OS permission;
- uses the same stable invocation ID;
- uses bounded attempts/backoff;
- does not automatically replay an unknown crash-recovery occurrence.

An unknown run requires explicit operator confirmation before retry.

A second simultaneously live scheduler is outside the current one-local-scheduler public-beta scope.

No new retry authority defect was found.

## 12. Automations -> Gateway

Automations supplies the stable `invocation_id` as Gateway's downstream idempotency identity.

Gateway wake ingestion:

- authenticates the caller at the Gateway edge;
- validates wake envelope;
- maps Automation scope to one Gateway workspace;
- creates a normal Gateway session/run;
- stores Automation binding metadata;
- uses the invocation ID for Gateway idempotency.

The contract is correct.

Its implementation is still affected by Gateway's non-linearizable first-claim race under `WSA-2026-008`.

Therefore duplicate Gateway runs for one simultaneous wake remain possible.

## 13. Automations -> Brain

Automations passes the stable invocation ID as the Brain idempotency key.

Brain action/receipt semantics:

- durably claim idempotent action identity;
- fail uncertain external effects closed;
- do not auto-retry uncertainty;
- replay completed duplicates from prior receipts.

A2.6 found no new cross-side Brain invocation identity conflict.

## 14. Automations -> Multiple Bots

A2.6 directly inspected the frozen Multiple Bots Automation ingress.

The receive side verifies:

- active native OS mode;
- Automation ID;
- invocation ID;
- workspace ID;
- fired timestamp;
- source kind/path;
- current source digest;
- projection digest;
- exact workspace activity;
- source containment/no symlink escape.

For Bot wake:

- target must be an active durable Bot in the same workspace;
- requested tools/connections cannot exceed Bot authority;
- normal approval gating is preserved;
- Task and lease IDs derive deterministically from invocation identity;
- exact replay returns the same Task/lease;
- changed objective/contract under the same invocation conflicts.

For Team Run wake:

- hard budgets are required;
- leader must have Worker creation authority;
- unresolved approval blocks creation;
- Task-only authority fields are rejected;
- exact replay returns the same Team Run.

Replay revalidates the current canonical Automation source digest, so a changed/removed source becomes a kill fence.

This satisfies the Automations-side claim that Multiple Bots honors source binding and invocation identity.

## 16. Data mutation events

Data mutations atomically bind:

- mutation effect;
- actor attribution;
- idempotency;
- immutable event;
- mutation receipt.

Automations may consume committed Data event facts.

Data does not become the scheduler.

Automations event ingress uses stable source event identity and digest so repeated events are replay-safe and changed payload under reused event identity fails closed.

Data's public scope-provenance defect remains `WSA-2026-020`.

## 17. Consent for permanent Bots

Current Gateway/OS composition distinguishes:

- temporary specialist Worker;
- recommendation;
- explicit durable Bot instruction/consent.

Verified behavior:

- temporary-only need does not create permanent Bot;
- advice/recommendation alone does not create Bot;
- repeated need does not equal consent;
- explicit consent creates exactly one conservative durable Bot;
- replay does not create another Bot;
- runtime cannot supply Bot IDs, scope, credentials or broader authority.

No new permanent-Bot consent defect was found.

## 18. Consent for Automations

Current Gateway/OS/Automations composition distinguishes:

- recurring need/recommendation;
- explicit recurring instruction;
- affirmative consent to a clear proposed cadence.

Creation requires complete schedule semantics.

Current controls include:

- cadence mismatch rejection;
- missing timezone rejection;
- recursive Automation creation suppression;
- stable owner idempotency;
- atomic Automation + trigger creation.

Repeated responsibility alone does not create a schedule.

No new consent defect was found.

## 19. Restart/recovery

### Gateway

Interrupted active runs become `paused_recovery_required`.

Gateway does not claim transparent arbitrary provider-process continuation.

Durable run/event state survives restart.

### Brain

Uncertain external effects become durable uncertainty and do not auto-retry.

### Multiple Bots

Execution queue/leases support stale recovery/dead-letter semantics.

### Automations

Crash-uncertain delivery becomes unknown and requires explicit retry confirmation.

### Data

Transactional effects are atomic and replay receipts are durable.

The main cross-system replay defect remains Gateway concurrency/idempotency `WSA-2026-008`.

## 21. Cross-side contradictions

### C-A2.6-001 - Automations stable invocation identity meets non-linearizable Gateway admission

Gateway concurrent first-claim admission can create duplicate runs.

**Finding:** existing `WSA-2026-008`.

### C-A2.6-002 - authenticated pause/cancel can be overwritten by stale Gateway execution state

Control requests are privileged and durable, but asynchronous execution can later save stale run state.

**Finding:** existing `WSA-2026-008`.

### C-A2.6-003 - Multiple Bots operator controls are not bound to trusted authenticated identity

Sensitive operator event/control paths use caller actor text as authority.

**Finding:** existing `WSA-2026-022`.

### C-A2.6-004 - generic Worker events can cross workspace before execution rejection

Generic Worker delegation/message state can be persisted for a foreign-workspace Worker.

**Finding:** existing `WSA-2026-023`.

### C-A2.6-005 - Automation lifecycle authority can conflict with legacy definitions

A later legacy schedule definition does not continuously fence canonical scheduler execution.

**Finding:** existing `WSA-2026-027`.
