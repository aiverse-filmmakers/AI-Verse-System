## 3. Primary owner-routed write spine

The supported mutation spine is:

`client/runtime -> Gateway -> OS authorization/action router -> canonical owner`

depending on the operation.

Gateway:

1. rejects runtime attempts to inject trusted authority/provenance fields;
2. derives trusted run/session/scope/evidence facts;
3. asks OS to authorize;
4. pauses for approval where required;
5. reauthorizes before effect;
6. asks OS to route the owner action;
7. stores only the Gateway result/receipt in Gateway run state.

OS host action routes currently include:

- migration.import;
- operator.profile.ensure;
- workspace.ensure;
- memory.capture;
- memory.session_digest;
- skills.learning-candidate;
- data.structured-truth;
- workers.temporary;
- bots.permanent;
- automations.create;
- bounded Data reads;
- capability instruction reads.

OS does not convert these requests into competing OS copies of Memory, Skills, Data, Bots or Automations truth.

## 4. Owner-specific write paths

### 4.1 OS

Normal writes stay inside OS owner surfaces.

The OS write-command boundary only canonically handles the OS-owned unclassified candidate inbox. It explicitly does not silently promote a candidate into Brain, Memory, Data, Skills, Connections or Automations.

Optional components may update their own extension registration/owned extension files under bounded registry contracts. Those registration writes do not transfer domain ownership.

### 4.2 Brain

Brain writes Brain-owned objects under its scoped Brain store.

External effects require both:

- Brain effective policy;
- OS/host permission.

Host denial wins, and permission is rechecked before dispatch.

The model/reasoner is advisory and cannot directly expand policy, permission, identity, privacy or scope.

#### Explicit bounded cross-owner exception: Brain -> OS handback

Brain directly writes one bounded OS strategic section during explicit direction handback.

This is **VERIFIED ALLOWED**, not a private-store bypass, because both independent sides define the same single-owner direction protocol:

- OS is default owner;
- explicit handover transfers strategic ownership to Brain;
- Brain handback exports current strategy into the bounded OS strategic section;
- unrelated OS current-state sections are preserved;
- write success is verified before ownership flips back to OS;
- direction registry writes are serialized;
- symlink/path safety is checked.

No dual direction owner is intended.

### 4.3 Memory

Memory canonical writes go through the hardened public Memory owner path.

OS/Gateway may request Memory capture or a session digest, but do not write Memory atomics themselves.

Native current sources are indexed in place and are not copied into a competing current-truth Memory store.

The Memory SQLite index is derived/disposable.

Existing authority defects remain:

- `WSA-2026-012` destructive lifecycle containment;
- `WSA-2026-013` write admission can diverge from lifecycle state;
- `WSA-2026-014` migration/authority handoff atomicity.

These are owner enforcement failures, not evidence of a second intended owner.

### 4.4 Skills

Skills is the only canonical writer of capability package/generation state.

Gateway/Brain/OS may propose or request learning, but:

- integrity is separate from admission;
- admission is separate from trust;
- trust/readiness are separate from authorization;
- production changes create a new immutable Skills generation;
- runtime cannot self-assert OS effect proof.

No sibling writes committed Skills generation bytes directly.

Existing lifecycle/retention findings remain `WSA-2026-016` through `018`.

### 4.5 Data

Canonical structured-data mutations go through Data's mutation engine.

The supported owner adapters preserve the boundary:

- Brain adapter is read-only;
- Memory bridge emits evidence/candidate material but does not auto-write Memory;
- Dashboard is read-only;
- Apps manifests do not grant Data authority;
- Multiple Bots adapter rechecks workspace/principal/task lease/capability;
- Connections integration does not silently create a bidirectional sync engine;
- Automations consumes committed Data event facts rather than becoming Data owner.

The exported public scope is structurally forgeable under `WSA-2026-020`, which can bypass trusted path provenance. That is a canonical Data admission defect, not a legitimate cross-owner write route.

### 4.6 Multiple Bots

Multiple Bots alone owns coordination state.

OS/Gateway/Automations may request owner operations.

Multiple Bots does not:

- open Data as a competing structured-data engine;
- own Memory or Brain;
- own scheduler state;
- own Connections credentials;
- let Dashboard become coordination truth.

The generic Worker workspace defect remains `WSA-2026-023`.

Operator authorization remains affected by `WSA-2026-022`.

### 4.7 Token

Token alone owns canonical normalized usage/pricing/cost truth.

Other components may emit or retain operational evidence.

That evidence is not canonical Token truth until admitted by Token.

The intended boundary is:

- Gateway runtime usage: run evidence;
- Multiple Bots usage: coordination budget/settlement evidence;
- automation/task/session/Bot/Worker IDs: attribution dimensions;
- Dashboard: read-only projection;
- Token: canonical normalization and money truth.

Multiple Bots explicitly declares:

- canonical Token owner = ai-verse-token;
- no canonical Token telemetry write here;
- no local pricing of usage;
- runtime cost = evidence, not canonical cost.

The remaining violation is internal to Token admission: `WSA-2026-024` allows generic ingest to self-assert ACTUAL without mandatory trusted-source proof.

No second canonical cost ledger was found.

### 4.8 Automations

Automations alone owns schedule/trigger/job truth.

Gateway/OS supplies consent/permission provenance, then the Automations owner bridge creates canonical definitions.

Brain and Bots adapters receive stable invocation identity while retaining their own domain state.

A Multiple Bots compatibility projection written under the OS automation area stores IDs/digests only and is explicitly projection-only. It is not canonical Bot state.

Existing schedule-authority/readiness defects remain:

- `WSA-2026-026`;
- `WSA-2026-027`;
- `WSA-2026-028`.

### 4.9 Connections

Connections alone owns:

- credentials/credential handles;
- connection state;
- admitted external capabilities;
- external approval state;
- provider-effect receipts.

Upstream components provide delegated capability and approval provenance.

Provider effects occur at the Connections final edge.

No sibling is intended to receive raw credential ownership.

Existing final-edge/system/origin defects remain `WSA-2026-030` through `033`.

### 4.10 Gateway

Gateway owns session/run edge truth only.

It does not open sibling canonical databases directly.

Runtime output cannot directly inject trusted:

- scope;
- actor/authorization;
- consent;
- owner provenance;
- idempotency;
- migration evidence.

Owner mutations are routed through OS/owner contracts.

Gateway Context Ladder fold state is derived and cannot replace raw run messages or Memory canonical history.

### 4.11 Dashboard

Current local Dashboard mutation routes are blocked.

Dashboard may own:

- selected system/window state;
- layout/presentation state;
- disposable cache/read models.

It must not own canonical OS/Brain/Memory/Skills/Data/Bots/Token/Automations/Connections state.

No direct canonical owner write was found in the current Dashboard implementation.

The current violation is **shadow meaning**, not direct storage mutation:

`WSA-2026-042` proves Dashboard synthesizes authoritative-looking Health/Inbox semantics from generic file observations.

### 4.12 Apps

Apps has no current runtime implementation.

No current canonical write path exists.

Its architecture explicitly requires future writes to respect OS/Data/Memory/Skills/Bots/Connections owner boundaries.

Direct private-store mutation remains forbidden.

### 4.13 Distribution

Distribution owns release/install receipt truth, not component domain truth.

Direct frozen implementation uses revision-bounded owner adapters/CLIs for OS, Brain, Memory, Skills, Data, Gateway, Automations, Multiple Bots and Token.

Distribution does not directly edit owner private canonical stores.

Its own receipt is not live component health truth. Status/doctor query owner surfaces.

The current defect is `WSA-2026-034`: concurrent Distribution lifecycle operations can overwrite a newer Distribution receipt after different owner effects complete.

### 4.14 System

System owns meta/spec/release evidence.

Distribution owns executable release-set selection/install truth.

System does not mutate product runtime state.

The present meta-shadow problem is already `WSA-2026-044`: several System current-state surfaces disagree with newer accepted owner/release evidence.

## 6. Duplicate-ledger analysis

### Gateway run evidence vs Memory

Not duplicate ownership.

Gateway run transcript/checkpoint state is canonical for run continuation/evidence.

Memory stores selective durable historical records/digests.

Raw transcripts are not automatically promoted wholesale into Memory.

### Gateway/Bots usage evidence vs Token

Not duplicate canonical cost truth.

Execution-local counters/budgets are operational evidence.

Token owns normalized telemetry/pricing/money truth.

### Memory SQLite index vs Memory Markdown

Not duplicate canonical truth.

Markdown atomics are canonical; SQLite is derived/disposable.

### Dashboard caches/read models vs owner state

Intended to be derived only.

Current synthetic semantics cross the line into shadow authority under `WSA-2026-042`.

### Distribution receipt vs live component state

Not duplicate health truth by contract.

Receipt says what Distribution installed. Live status/doctor comes from owners.

Concurrent receipt writes remain defective under `WSA-2026-034`.

### System release evidence vs Distribution release-set manifests

Different authority classes:

- Distribution = executable release-set/install selection;
- System = meta/release evidence and architecture truth.

They must agree on current release facts. Existing drift is `WSA-2026-001` and `WSA-2026-044`.

### Automations schedule state vs OS attachment state

Not intended as duplicate schedule truth.

Automations owns schedules; OS registry only records extension attachment.

Lifecycle/readiness divergence is already `WSA-2026-028`.

## 7. Brain/model security-authority check

No supported write path allows model output alone to become security authority.

Verified layered behavior:

- model reasoning is advisory;
- Brain deterministic policy cannot be weakened by caller override;
- OS/host permission is an independent outer gate;
- host denial always wins;
- approved effects are reauthorized before dispatch;
- Gateway strips/rejects runtime-supplied trusted authority/provenance fields;
- Gateway derives run/session/scope/evidence itself;
- new permanent Bots/Automations require explicit consent;
- Connections effects require delegated capability/approval at the Connections edge.

Later A2.4 will audit authentication/principal binding in depth.

Current related defects remain existing findings, especially `WSA-2026-022`, `030`, `031`, `032`.
