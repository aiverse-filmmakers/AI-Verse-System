## 3. Current security model

The current public-beta security model is effectively **single-operator / local-first**, not a hosted multi-user RBAC model.

That does not mean identity is ignored.

The current layers are:

1. **Gateway transport authentication** proves the bearer principal.
2. **Gateway session/run binding** binds one system/workspace/principal.
3. **OS scope authorization** evaluates operator/workspace policy.
4. **Owner component admission** rechecks its own domain/scope invariants.
5. **Connections final edge** rechecks current connection/capability/effect authority.
6. **Provider/runtime actors** remain provenance identities unless explicitly bound to trusted authorization.

The intended rule is:

`authenticated transport identity != provenance actor != domain authority`

unless an owner explicitly binds them.

## 4. Gateway authentication and session identity

Direct Gateway code proves:

- bearer tokens are verified using salted scrypt;
- successful bearer verification returns a configured principal;
- caller `x-actor-id` is not authentication;
- all application routes except minimal health require bearer auth;
- rate limiting is keyed by authenticated principal;
- session creation binds:
  - system_id;
  - workspace_id;
  - principal;
- run creation repeats the same binding;
- run read/control surfaces require principal ownership;
- an existing session cannot be silently rebound to a conflicting system or principal;
- browser Origin validation is additional browser policy, not authentication.

Current Gateway setup creates one bearer identity by default.

No current claim of hosted multi-user RBAC is made.

## 5. Gateway -> OS authority handoff

Gateway runtime output cannot supply trusted:

- scope;
- principal;
- actor;
- approval;
- authorization;
- idempotency;
- durable owner IDs;
- trusted provenance.

Gateway derives the run-bound scope itself.

For owner actions it builds a bounded OS request containing:

- action class;
- operator/workspace scope;
- operation;
- trusted parameters;
- idempotency key;
- request fingerprint;
- scope/budget/reversibility evidence.

OS action permission v1 accepts only a strict request field set and validates exact scope.

The OS permission layer is deliberately **scope/policy based**, not a second user-authentication service.

It evaluates:

- operator permission policy;
- workspace permission policy;
- workspace active/paused/archived state;
- action class;
- approval requirement.

This is coherent with the current single-operator model.

## 6. Gateway approval identity

Approval of a pending Gateway effect requires the authenticated principal to own the run.

Gateway then re-calls OS authorization immediately before the effect and includes the authenticated approving principal in the approval object.

Therefore model output or an unrelated authenticated principal cannot approve another principal's run through the normal Gateway route.

Gateway then calls OS owner routing only after the recheck.

## 7. System and workspace identity

### OS

OS enforces:

- constrained workspace IDs;
- physical workspace containment;
- realpath/symlink boundaries;
- workspace manifest ID matching;
- paused/archived workspace denial;
- operator-vs-workspace context boundaries;
- no arbitrary cross-workspace private capability selection.

### Gateway

Gateway has one configured system ID.

Runs and sessions bind that system ID plus one workspace and principal.

Progressive/fold/archive data is scoped by:

- system;
- workspace;
- principal.

Cross-workspace retrieval fails closed.

### Dashboard

Dashboard has its own independent systemId registry for UI projection.

Its current system-root binding is defective under `WSA-2026-039`, and its local scratch Gateway is unauthenticated under `WSA-2026-040`.

Dashboard is not the production authentication authority.

## 8. Brain scope and authority

Brain supports deterministic scopes:

- operator;
- workspace:<id>.

It owns strategy/Goals only after explicit direction ownership.

Brain does not authenticate users independently.

External action authority is the intersection of:

- Brain's own restrictive policy;
- host/OS permission.

Host denial wins.

Model/reasoner output cannot expand:

- permission;
- privacy;
- system/workspace scope;
- identity;
- credentials.

The current path-containment defect remains `WSA-2026-009`.

## 9. Memory visibility

Memory native workspace recall normally sees:

- requested workspace;
- operator context.

It does not normally include unrelated workspace history.

Memory also has an explicit `all_workspaces` retrieval mode.

Memory correctly states that it is not the ACL or multi-user permission engine.

A2.4 therefore treats broad Memory retrieval as a **host-authorized privileged read surface**, not as proof that Memory itself authenticates principals.

Current Gateway scoped retrieval does not silently expand into unrelated workspace history.

A4/A2.5 retain responsibility for adversarial broad-read tests.

## 10. Data scope provenance

Data's native `TrustedDataRoot` model is strong:

- trusted root canonicalization;
- workspace path containment;
- workspace manifest identity;
- database scope binding.

However, public client scope is structurally forgeable.

A caller can provide a shape-compatible `DataDatabaseScope` without proving it was produced by `TrustedDataRoot`.

This remains existing HIGH finding:

`WSA-2026-020`

This is the primary Data identity/isolation defect.

## 11. Multiple Bots identities

Multiple Bots has several distinct identities:

- durable Bot;
- temporary Worker;
- Task;
- Team Run;
- coordination actor/provenance;
- authenticated transport principal.

The managed Team Run path strongly binds:

- Worker;
- Task;
- workspace;
- Team Run;
- capability lease;
- environment lease;
- execution ownership;
- budget.

Two current defects remain.

### 11.1 Operator identity binding

Remote Gateway/Tailscale bearer authentication proves transport access.

Sensitive operator actions still accept caller-supplied actor identity without binding that actor to trusted authenticated operator identity.

This remains:

`WSA-2026-022`

### 11.2 Worker workspace identity

Generic Worker coordination paths do not preserve the same workspace invariant as the managed Team Run path.

A foreign-workspace Worker can receive persisted coordination state before the runner rejects execution, and failure handling can still mutate the real Worker.

This remains:

`WSA-2026-023`

## 12. Token authorization envelopes

Token deliberately does not authenticate users itself.

Its read surfaces require an authorization envelope supplied by the trusted outer host.

That contract is valid because Token is an owner service behind the host boundary.

Token then imposes an immutable filter floor across dimensions including:

- workspace;
- Bot;
- Worker;
- Skill;
- automation;
- run;
- task;
- session.

Requested conflicting scope fails closed.

Gateway projection is read-only and also requires the host authorization envelope.

No Token evidence was found that treats a raw caller principal string as independently authenticated authority.

Token's current HIGH defect `WSA-2026-024` concerns monetary-source authority, not user authentication.

## 13. Automations identity and scope

Automations does not grant execution authority from schedule membership alone.

Before every delivery attempt it asks OS action permission with:

- exact action class;
- exact operator/workspace scope;
- immutable request fingerprint.

Permission results must bind back to those exact values.

Approval-required is not treated as approval.

Retries re-check current OS authority.

Automations owner adapters preserve downstream identities:

- Brain gets stable invocation ID as idempotency identity;
- Multiple Bots requires workspace scope and bounded target;
- Gateway receives stable wake envelope.

Webhook ingress has its own HMAC/replay protections and is loopback-first.

Current Automation findings concern canonical store/lifecycle authority, not a newly discovered principal-authentication defect.

## 14. Connections delegated authority

Connections intentionally separates:

- connection registration;
- live verification;
- capability admission;
- connection approval;
- per-action approval.

The service API accepts trusted delegated capability and approval evidence from an upstream host.

Connections does not claim to authenticate that upstream caller itself.

That is acceptable only if the caller is already inside a trusted host boundary.

In the current public-beta release, Connections is not part of the Agent profile, so there is no currently supported end-user Agent journey that depends on this inbound delegated-auth seam.

Its internal current defects remain:

- `WSA-2026-030`: installation system binding not enforced;
- `WSA-2026-031`: MCP credential-origin isolation bypass on reauth;
- `WSA-2026-032`: incomplete final-edge lifecycle/budget recheck;
- `WSA-2026-033`: normalized path authorization bypass.

These remain the blocking authority issues for future Full-profile use.

## 15. Credential identity and origin

Raw credential ownership remains Connections-only.

Current verified laws include:

- Gateway stores provider secret environment-variable names, not provider secret values;
- OS runtime envelopes reject raw credential/token/api-key fields;
- Token schema has no prompt/response/credential columns;
- Automations target configuration rejects inline credentials;
- Multiple Bots does not become credential owner;
- Dashboard is projection-only;
- Connections uses credential handles and injects credentials at provider edge.

The current cross-origin credential defect is exactly `WSA-2026-031`.

## 16. Dashboard authentication/isolation

Dashboard scratch Gateway is local-only but unauthenticated.

A non-browser local process can enumerate systems/workspaces and read current projections.

This remains:

`WSA-2026-040`

Additional Dashboard identity defects:

- `WSA-2026-039`: systemId can silently follow a replaced filesystem root;
- `WSA-2026-038`: one WebSocket can retain a prior workspace subscription after switching;
- `WSA-2026-041`: normal localhost browser Origin ports are rejected.

These are Dashboard-layer issues, not production Gateway identity failures.

## 17. Distribution identity/scope role

Distribution does not authenticate end users and does not grant domain authority.

It binds one installation receipt to:

- root;
- profile;
- release set;
- component selection.

It invokes owner lifecycle surfaces at revision-bounded adapters.

Distribution must not invent workspace permissions, Bot authority, Token authority, Connections approval or Brain direction ownership.

No such authority expansion was found.

## 18. System meta identity

AI-Verse-System is not part of the runtime authentication chain.

It records architecture/release evidence.

No product runtime accepts System documents as live authentication tokens or permission grants.

## 19. End-to-end current Agent trust chain

### Interactive run

`bearer credential -> Gateway principal -> session/run system/workspace/principal binding -> Gateway-derived action request -> OS operator/workspace permission -> owner admission -> effect`

### Approved consequential action

`bearer principal owning run -> explicit approval -> OS reauthorization -> owner final admission -> effect receipt`

### Automation wake

`Automations canonical trigger/run -> stable invocation identity -> authenticated Gateway wake route -> Gateway principal/system/workspace run binding -> normal OS/owner action authority`

The Gateway idempotency race remains `WSA-2026-008`, but identity binding itself is preserved on the normal path.

### Multiple Bots

`trusted host/Gateway transport -> Multiple Bots owner admission -> Bot/Worker/Task/Team Run scope checks`

Operator and generic Worker gaps remain `WSA-2026-022` and `023`.

### Token read projection

`trusted host authorization envelope -> immutable Token scope filter -> read-only projection`

### Future Connections effect

`trusted host delegated capability/approval -> Connections current connection/capability/system/workspace/final-edge checks -> provider credential injection/effect`

Current Connections defects must be repaired before Full-profile dogfood.

## 20. Cross-side contradictions

### C-A2.4-001 - authenticated transport principal is not bound to Multiple Bots operator authority

Gateway/Tailscale bearer proves transport access, while sensitive Multiple Bots controls accept caller-supplied actor identity as operator authority.

**Finding:** existing `WSA-2026-022`.

### C-A2.4-002 - managed Worker scope is stronger than generic Worker scope

Managed Team Run Workers are workspace-bound, but generic Worker delegation/message paths can cross workspace before failure.

**Finding:** existing `WSA-2026-023`.

### C-A2.4-003 - trusted Data scope contract is not enforced by public client provenance

Data documentation requires TrustedDataRoot-derived scope, but exported structural scope objects can be forged.

**Finding:** existing `WSA-2026-020`.

### C-A2.4-004 - Connections installation system identity is not authoritative

Connections setup records one system ID, but connection creation/execution can use another.

**Finding:** existing `WSA-2026-030`.

### C-A2.4-005 - Connections credential origin binding is bypassable during reauth

Initial MCP registration protects bearer-handle origin reuse, but reauth does not apply the same check.

**Finding:** existing `WSA-2026-031`.

### C-A2.4-006 - Dashboard local projection server has no authenticated principal

Dashboard scratch Gateway exposes read projections to any local client able to connect.

**Finding:** existing `WSA-2026-040`.

### C-A2.4-007 - Dashboard system/workspace identity can drift after registration/subscription

Registered root replacement and stale WebSocket subscription can change effective system/workspace context without the UI's intended identity transition.

**Findings:** existing `WSA-2026-038`, `039`.

## 21. No new principal propagation finding

A2.4 specifically examined whether Gateway failing to forward its bearer principal as a first-class OS permission field is itself a defect.

It is **not classified as a new defect in the current public-beta model** because:

- Gateway default setup creates one operator bearer identity;
- OS permission is intentionally defined over operator/workspace scope, not hosted user RBAC;
- Gateway itself enforces run ownership by bearer principal;
- explicit approval requires that same run-owning authenticated principal;
- OS policy remains an independent outer permission floor;
- no current claim says different Gateway principals have different OS action policy.

If future multi-user principals are introduced, this boundary must be redesigned or explicitly versioned.

A4 may still adversarially test manually configured multiple Gateway bearer principals.
