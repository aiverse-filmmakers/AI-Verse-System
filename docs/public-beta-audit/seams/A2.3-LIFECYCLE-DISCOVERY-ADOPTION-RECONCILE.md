## 3. Current Agent lifecycle spine

The supported current Agent lifecycle is:

`Distribution release selection -> exact source acquisition -> OS setup -> component owner install/setup -> owner/OS attachment -> owner status/doctor -> composed start -> owner-routed operation -> bounded reconcile/recovery`

For supported component lifecycle changes:

`Distribution -> owner lifecycle command -> owner state transition -> Distribution receipt update`

Distribution does not replace owner lifecycle truth.

The OS local extension registry is discovery/attachment metadata. It is not a second copy of component canonical domain state.

## 4. Release selection and install order

### 4.1 Distribution selection

Distribution selects one admitted immutable release set and locks:

- system root;
- profile;
- release set;
- component selection.

A different profile/root/release/selection cannot silently replace an existing lock.

The current default Agent profile contains:

- OS;
- Brain;
- Memory;
- Skills;
- Data;
- Gateway;
- Automations;
- Multiple Bots;
- Token.

Connections, Dashboard and Apps remain outside the current Agent release.

### 4.2 Clean install

Distribution's accepted Agent path performs exact source acquisition and setup through owner interfaces.

Clean-machine Agent acceptance already exercises the real composed installation rather than an internal shortcut.

### 4.3 Install-order independence

OS A1 evidence proves install-order tolerance for the earlier five-component foundation through the accepted three-order gate.

Current Agent composition is controlled by Distribution's ordered setup path and exact accepted release set.

Optional owner components use local registration/discovery rather than requiring OS source mutation.

No whole-system requirement was found that every arbitrary permutation of nine Agent components must be supported.

## 5. OS lifecycle role

OS lifecycle is currently:

- install: VERIFIED;
- setup: VERIFIED and idempotent;
- status: VERIFIED;
- doctor: VERIFIED with depth;
- update: VERIFIED, clean-tree/fast-forward and user-state preserving;
- reinstall: VERIFIED;
- component discovery: VERIFIED through local extension/provider surfaces;
- reconcile: VERIFIED and owner preserving;
- migration/import: VERIFIED through owner-routed paths;
- destructive OS root uninstall: intentionally not offered.

OS does not invent lifecycle verbs a component does not support.

OS remains the host/discovery/permission floor, not the owner of sibling lifecycle state.

## 6. Brain lifecycle

Current Brain lifecycle supports:

- install/setup;
- native attachment;
- explicit initialization;
- migration/adoption;
- status/doctor;
- update/migrate;
- disable/detach/uninstall;
- standalone and native modes;
- explicit direction handover/handback separate from installation.

Important rule:

Installing or setting up Brain does not silently transfer strategic direction.

Strategic ownership changes only through the explicit direction protocol.

Current lifecycle defects remain:

- `WSA-2026-009`: native filesystem containment can escape through parent symlink conditions;
- `WSA-2026-010`: Goal operation concurrency/replay;
- `WSA-2026-011`: release/version identity drift.

These defects impair the lifecycle but do not create ambiguity about the intended owner graph.

## 7. Memory lifecycle

Memory supports standalone/native installation and OS discovery through compatibility/registry surfaces.

Intended lifecycle:

- install;
- setup;
- attach/discover;
- status/doctor;
- write/read;
- update;
- disable/detach;
- uninstall preserving canonical historical state;
- migration/adoption;
- reinstall.

The current lifecycle is materially contradicted by existing findings:

- `WSA-2026-012`: destructive lifecycle path containment;
- `WSA-2026-013`: canonical writes can remain admitted when component lifecycle/attachment says they should not;
- `WSA-2026-014`: migration/authority handoff can be non-atomic;
- `WSA-2026-015`: release/bootstrap drift.

The important cross-component result is that OS discovery/attachment and Memory write authority are intended to align, but current Memory enforcement can diverge from that lifecycle state.

## 8. Skills lifecycle

Skills lifecycle is generation based:

2. verify;
3. commit immutable generation;

5. pin exact generation for execution.

Supported lifecycle includes:

- install;
- setup;
- readiness;
- update;
- rollback;
- disable/enable where supported;
- uninstall while preserving generation/history needed by policy;
- recovery.

Existing defects:

- `WSA-2026-016`: lifecycle controller containment;
- `WSA-2026-017`: a long-lived owner lock can be reclaimed while still live;
- `WSA-2026-018`: retention can remove an in-use pinned generation;
- `WSA-2026-019`: release/bootstrap identity drift.

The lifecycle graph itself is coherent, but it is not safe enough for dogfood until the blocking containment and serialization defects are repaired.

## 12. Automations lifecycle and discovery

Automations supports:

- install;
- setup;
- status;
- doctor;
- enable;
- disable;
- update;
- uninstall;
- OS extension attachment;
- owner bridge.

Two lifecycle contradictions are material.

### 12.1 Legacy schedule authority fence

At setup, legacy OS automation definitions can force migration-required.

After setup, the same conflict is not a continuous execution/readiness fence.

A legacy definition appearing later can coexist with an active canonical Automations scheduler.

This is existing `WSA-2026-027`.

### 12.2 OS attachment divergence

Automations component lifecycle and OS extension lifecycle are not synchronized:

- component disable may leave OS registry enabled;
- component enable may coexist with registry disabled;
- uninstall can leave the registry entry and bridge files.

The retained bridge fails closed if owner readiness is gone, which bounds residual execution authority.

This remains existing `WSA-2026-028`.

## 15. Distribution lifecycle coordination

Distribution is the system-level lifecycle coordinator for the supported release set.

It:

- acquires exact sources;
- stages runtime/dependency state;
- invokes owner install/setup;
- asks owner status/doctor;
- invokes owner enable/disable/uninstall/update where supported;
- refuses direct destructive OS root deletion;
- records installation/release receipt;
- performs bounded reconcile;
- preserves owner canonical state.

Same-set update/rollback is accepted.

Changed cross-release update is intentionally fail-closed because no changed transition is currently admitted.

That is not a bug.

The Safe Update release-train project remains incomplete, so changed cross-release migration/rollback must stay closed until separately admitted.

Current Distribution lifecycle defect:

- `WSA-2026-034`: no cross-process lifecycle transaction, so stale Distribution receipt commits can follow different completed owner effects.

## 20. Discovery and readiness graph

Current discovery is layered rather than one global readiness bit.

- OS discovers registered optional components/providers.
- Distribution records what it installed.
- Each component owner reports status/doctor.
- OS may compose owner readiness.
- Distribution queries owners rather than treating its receipt as live health truth.
- Gateway consumes owner/host availability.
- Dashboard is intended to project owner truth rather than invent it.

Important existing disagreements:

- Automations component lifecycle vs OS registry: `WSA-2026-028`;
- Memory lifecycle state vs write admission: `WSA-2026-013`;
- Gateway lifecycle/status truth: `WSA-2026-007`;
- Dashboard synthetic health: `WSA-2026-042`.

## 21. Reconcile graph

OS reconcile is owner preserving.

Distribution safe reconcile is bounded and does not authorize arbitrary strategic or domain changes.

Current first-run self-heal is intentionally narrow.

It may perform only admitted reversible setup/reconcile actions and does not silently:

- transfer Brain strategy ownership;
- create credentials/Connections;
- create recurring Automations;
- create permanent Bots;
- widen permission;
- invent owner migration.

Unsupported or ambiguous reconcile actions fail closed.

## 22. Disable, detach and uninstall graph

### State preservation law

Normal component uninstall/detach is software/lifecycle removal, not deletion of canonical user/domain state.

Verified preservation intent:

- Brain state preserved;
- Memory history preserved;
- Skills generations/history preserved according to lifecycle policy;
- Data databases preserved;
- Multiple Bots coordination DB preserved;
- Token ledger/pricing preserved;
- Automations canonical scheduler DB preserved;
- Connections state preserved on non-purge uninstall.

### Unsafe exceptions already found

- Gateway destructive lifecycle: `WSA-2026-006`;
- Memory destructive lifecycle: `WSA-2026-012`;
- Skills controller containment: `WSA-2026-016`;
- Connections purge: `WSA-2026-029`.

These are the primary current data-loss/filesystem lifecycle blockers.

## 23. Update and rollback graph

Current supported update law:

- component owner controls component state migration;
- Distribution controls compatible software release transition;
- unknown migration means stop;
- user/canonical state is preserved;
- rollback is software rollback unless owner explicitly supports state rewind.

Current reality:

- same-set Distribution update/rollback: accepted;
- changed cross-release transition: no admitted edge, fail-closed;
- component local update paths exist;
- release identity drift exists in Brain/Memory/Skills/Data;
- future changed release transitions require Safe Update acceptance before they become supported.

No unsupported changed transition is falsely represented as current functionality.

## 25. Cross-side contradictions

### C-A2.3-001 - Automations owner lifecycle and OS discovery lifecycle diverge

OS registry is intended to represent attachment/enabled discovery while Automations owner state controls schedule execution.

Automations lifecycle does not keep the registry synchronized.

**Finding:** existing `WSA-2026-028`.

### C-A2.3-002 - canonical Automations scheduler can continue after a new legacy-authority conflict appears

The anti-dual-scheduler fence is evaluated during setup but not continuously during scheduler execution/readiness.

**Finding:** existing `WSA-2026-027`.

### C-A2.3-003 - Distribution depends on owner lifecycle contracts that contain destructive containment defects

Distribution correctly calls owner lifecycle surfaces instead of private stores.

However, invoking a supported owner lifecycle does not make the owner implementation safe.

Current affected owners:

- Gateway: `WSA-2026-006`;
- Memory: `WSA-2026-012`;
- Skills: `WSA-2026-016`;
- Connections purge if later admitted: `WSA-2026-029`.

No duplicate finding is opened.

### C-A2.3-004 - Distribution receipt can diverge from the owner effects it coordinates

Owner calls can complete while concurrent Distribution processes later overwrite receipt truth.

**Finding:** existing `WSA-2026-034`.
