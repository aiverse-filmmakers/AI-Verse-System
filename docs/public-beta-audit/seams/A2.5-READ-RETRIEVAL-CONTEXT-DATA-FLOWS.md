## 3. Current context read spine

The normal interactive read path is:

`Gateway -> OS host -> current context + capabilities + Connections metadata + Memory progressive retrieval -> bounded runtime context`

Gateway does not open sibling canonical stores directly.

The current context path deliberately combines owner projections while preserving each owner's truth class.

## 4. OS current context

OS owns current host/operator/workspace context and strategic-owner resolution.

Current context:

- is scope bound;
- physically resolves workspace state;
- honors current direction owner;
- removes/fences stale OS strategic sections while Brain owns direction;
- reports unavailable Brain-owned strategy rather than silently falling back to frozen OS strategy;
- includes bounded owner projections rather than raw private sibling stores.

OS capability discovery likewise remains separate from execution permission.

## 5. Gateway progressive context

Gateway Context Ladder behavior is strongly bounded.

### Current owner context

Normal assembly requests:

- host description;
- current OS context;
- capability list;
- bounded Connections metadata;
- Memory progressive history.

### Pressure handling

Context governor:

- does not compact low-pressure context;
- may schedule derived fold work under soft pressure;
- compacts only older prefixes under hard pressure;
- preserves the configured recent raw tail;
- keeps persisted `run.messages` canonical;
- fails closed when pressure cannot be safely resolved.

### Runtime deep-context tool

The runtime may use only bounded `aiverse_context`.

It cannot supply:

- scope;
- workspace;
- workspace_id;
- principal;
- system_id;
- permissions;
- authorization.

Allowed inputs are bounded retrieval intent only.

## 6. Memory retrieval truth classes

Memory has a clean four-depth model:

- catalog;
- summary;
- detail;
- source.

### Catalog / orientation

Derived and rebuildable.

Does not copy canonical body text into a competing truth store.

### Summary/detail

Navigation/derived retrieval.

Not exact evidence.

### Source

Exact-source retrieval:

- revalidates scope;
- revalidates path;
- revalidates current source version;
- returns stale/unavailable rather than silently serving changed evidence;
- preserves provenance.

Memory relationship projection is likewise derived from explicit provenance metadata rather than inferred body text.

## 7. Session digest boundary

Session digests are compact durable historical records, not raw transcripts.

Gateway raw transcript remains external exact-evidence authority.

Digest promotion:

- is capped;
- cannot cross digest scope;
- can reference only evidence already covered by the digest;
- routes promoted durable facts through Memory capture gates;
- does not automatically make a summary canonical exact truth.

This separation is correct.

## 8. Gateway exact fallback

For session-digest evidence requiring raw Gateway source:

1. Memory returns an external-source reference plus source fingerprint.
2. Gateway resolves the referenced canonical completed run.
3. Gateway rechecks:
   - system;
   - principal;
   - workspace visibility;
   - source fingerprint.
4. Fingerprint mismatch returns stale and no raw messages.

Integrated tests prove the real Gateway -> OS -> Memory -> Gateway exact-source composition.

## 9. New stale-cache defect

Gateway's per-run deep-context dedupe cache bypasses the freshness checks described above.

### Implementation

For each unique deep retrieval, Gateway stores:

- request fingerprint;
- tool call ID;
- depth;
- query fingerprint;
- result digest;
- source-read flag;
- byte counts;
- timestamp.

The cache record does **not** store or bind:

- owner source version;
- source fingerprint;
- current source generation/version.

For a repeated identical request:

1. Gateway finds the prior request fingerprint.
2. It does not call the owner.
3. It does not run exact-source freshness validation.
4. It may parse the prior tool result from canonical run messages.
5. It returns that old result under top-level `status: cached`.

The test suite explicitly asserts that an equivalent second request must not hit the owner twice.

### Cross-side contradiction

Memory and Gateway exact-source contracts say stale source fingerprints fail closed on source retrieval.

The per-run cache can prevent source retrieval from happening at all.

If the underlying Memory exact source or Gateway external raw source changes after the first exact read, a repeated identical request can replay the old exact result without checking the current source fingerprint/version.

This opens `WSA-2026-045`.

## 10. Brain read/retrieval

Brain consumes current context and has bounded meaningful retrieval.

Brain does not become the Memory owner.

Strategic evaluation:

- uses fresh-context requirements for stronger evidence levels;
- keeps model inference separate from deterministic completion truth;
- reads external-owner state through bounded host contracts;
- does not let retrieval expand permission or scope.

No separate Brain read-owner contradiction was found.

## 11. Skills read path

Skills read/execution flow binds:

- provider;
- capability ID;
- exact immutable generation;
- package digest;
- verified package containment.

Execution rechecks the selected generation and package digest before reading instructions.

The main read-side lifecycle risk remains existing `WSA-2026-018`: retention can remove a generation that a valid live execution pinned earlier.

That is already registered and not duplicated.

## 12. Data read flow

Data public query uses a bounded structured query AST rather than raw SQL.

Read boundaries preserve:

- one workspace database;
- scope binding;
- bounded result shape;
- authorization context in result provenance.

Adapters preserve owner semantics:

- Brain: read-only;
- Dashboard: read-only;
- Bots: rechecks workspace/principal/task lease/capability;
- Apps: future host-bound capability model;
- Memory bridge: evidence/provenance-oriented rather than automatic Memory mutation.

Current scope-provenance weakness remains `WSA-2026-020`.

## 13. Dashboard read projections

Dashboard currently reads OS/workspace sources through server-side path resolution.

Strengths include:

- systemId/workspaceId protocol;
- no arbitrary browser root parameter;
- traversal rejection;
- realpath containment;
- symlink escape rejection;
- SQLite read-only/query-only access;
- source-preview size/type limits;
- cache namespacing.

Current read defects remain:

- `WSA-2026-039`: systemId may follow replaced root;
- `WSA-2026-040`: local read server is unauthenticated;
- `WSA-2026-042`: synthetic Health/Inbox semantics create shadow owner meaning.

These defects affect the projection layer but do not create a second canonical database.

## 19. WSA-2026-045 - repeated Gateway deep-context reads can replay stale exact-source evidence

**Severity:** MEDIUM  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** retrieval freshness / provenance cache invalidation  
**Affected repo:** `AI-Verse-Gateway`

### Summary

Gateway correctly revalidates owner/source freshness during a real exact-source read.

But its per-run deep-context dedupe cache keys only on the retrieval request, not the current source version/fingerprint.

After an exact result is cached, a repeated identical request can return the prior result without consulting Memory or revalidating Gateway raw-source fingerprint.

### Deterministic trace

1. exact deep retrieval request succeeds;
2. Gateway stores request fingerprint and result digest;
3. underlying Memory source or external Gateway raw source changes;
4. runtime makes the same deep retrieval request again;
5. Gateway finds the same request fingerprint;
6. Gateway returns cached result;
7. no owner call or source-fingerprint revalidation occurs.

The returned top-level status is `cached`, but the embedded prior exact result remains available as the retrieval content.

### Impact

Within one long-running run, a model/user asking again for the same exact evidence can receive stale exact content even though the current owner/source would now reject it as stale or return changed content.

This is a correctness/provenance defect.

It does not itself expand authority or cross scope, so A2.5 classifies it MEDIUM rather than HIGH.

### Required closure evidence

After repair authorization:

- exact-source cache entries must bind the source version/fingerprint they validated;
- repeated exact-source requests must revalidate that version/fingerprint before replay;
- changed source must return stale or perform a fresh owner read;
- summary/detail caching may retain separate explicitly versioned semantics if desired;
- add Memory source-drift and Gateway external-source-drift regression tests;
- preserve scope/principal checks on cache replay.
