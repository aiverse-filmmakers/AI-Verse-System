## 3. Graph model

A6.2 uses three node classes.

### 3.1 Primary root-cause family

A recurring architectural failure pattern that directly explains one or more findings.

### 3.2 Finding node

One stable `WSA-2026-NNN` record with its own evidence, impact and closure requirement.

### 3.3 Relationship edge

A relationship between root-cause families:

- **AMPLIFIES** — one root makes the impact/race/recovery behavior of another worse;
- **OBSCURES** — one control-plane root makes current truth harder to identify;
- **MASKS IN QUALIFICATION** — an evidence root can allow an implementation root to survive release gates;
- **INDEPENDENT** — no causal dependency was proven.

The graph avoids claiming strict causality where the audit only proved co-occurrence or incomplete qualification.

## 5. RC-01 - Trusted boundary binding is not consistently enforced at the final read/write/effect edge

**Findings:**  
`WSA-2026-006`, `009`, `012`, `016`, `020`, `022`, `023`, `024`, `029`, `030`, `031`, `032`, `033`, `038`, `039`, `040`, `051`

**Severity:** 4 BLOCKER / 13 HIGH

### Root statement

AI-Verse has strong architectural concepts for:

- canonical owner;
- system/workspace scope;
- filesystem root;
- operator identity;
- credential origin;
- provider path;
- private-network policy;
- monetary source authority.

But several executable boundaries accept a weaker representation of that authority than the architecture assumes.

Examples include:

- pathname equality without physical-root confinement;
- caller-supplied or structurally valid scope without trusted provenance;
- actor/domain identifiers without authenticated identity binding;
- setup-time system binding not enforced at later execution;
- credential handles whose origin is not re-bound at reauth;
- policy checks performed before a later independently resolved network effect;
- local read APIs assuming loopback is sufficient authority.

The recurring law is:

> **Trusted scope/identity/path/network/source authority must be bound to canonical trusted context and revalidated at the final read, write or external-effect edge.**

### Affected journeys

### Adversarial confirmation

## 6. RC-02 - Canonical mutations rely on non-transactional read/check/write, weak serialization, or non-atomic handoff

**Findings:**  
`WSA-2026-008`, `010`, `014`, `017`, `025`, `034`, `052`, `053`, `054`, `055`

**Severity:** 7 HIGH / 3 MEDIUM

### Root statement

Multiple owners correctly implement semantic checks such as:

- “has this idempotency key already been claimed?”;
- “does this Goal already own this operation ID?”;
- “is this lifecycle lock stale?”;
- “has this migration source already been imported?”;
- “does this natural-key record already exist?”;
- “has this external effect already been reserved/executed?”;
- “is this receipt still the newest lifecycle truth?”.

The recurring weakness is that the semantic check and the canonical effect are not always protected by one atomic transaction, durable compare-and-set, live-owner lock, or failure-atomic handoff.

The recurring law is:

> **If uniqueness, idempotency, authority handoff or lifecycle truth depends on a read/check, the check and canonical mutation must be serialized/transactional at the same ownership boundary.**

### Affected repos

## 7. RC-03 - Lifecycle/readiness truth is duplicated instead of being operationally authoritative

**Findings:**  
`WSA-2026-007`, `013`, `026`, `027`, `028`, `056`

**Severity:** 4 HIGH / 2 MEDIUM

### Root statement

Several components have lifecycle/readiness metadata that can disagree with whether the component is actually allowed and able to act.

Examples:

- Gateway config/status can say one lifecycle state while live process behavior remains another;
- Memory native writes can proceed independently of owner lifecycle authority;
- Automations can mutate a SQLite file before proving it is the canonical owned store;
- legacy schedules can become live after setup even though migration conflict was previously checked;
- component lifecycle and OS attachment lifecycle can diverge;
- Connections health can remain green while canonical receipt state is unreadable.

The recurring law is:

> **Lifecycle/readiness must be derived from the canonical owner’s operational state, and that state must gate every canonical action—not only setup-time checks or metadata.**

### Affected repos

AI-Verse-Gateway, AI-Verse-Memory, AI-Verse-Automations, AI-Verse-Connections.

### Affected seams

A2.2, A2.3, A2.6.

### Affected journeys

A3.2, A3.3, A3.7, A3.10.

### Adversarial confirmation

A4.3 partial failure/corruption/recovery.

## 8. RC-04 - Long-lived state lacks generation-aware retention, freshness invalidation, or bounded indexing

**Findings:**  
`WSA-2026-018`, `045`, `058`, `059`

**Severity:** 4 MEDIUM

### Root statement

The system is designed for long-lived use, but several state paths were implemented as short-lived/simple collections without enough lifecycle metadata.

Examples:

- Skills retention cleanup does not know which immutable generation is still actively pinned;
- Gateway deep-context cache can replay exact-source data after the source changed;
- Gateway idempotency history grows as one full-read/full-rewrite file;
- Connections budget/idempotency execution scans lifetime receipt history.

The recurring law is:

> **Long-lived canonical/derived state needs explicit freshness identity, active-generation references, retention rules and indexed/bounded lookup behavior.**

### Affected repos

AI-Verse-Skills, AI-Verse-Gateway, AI-Verse-Connections.

### Affected seams/journeys

A2.5; A3.3, A3.4, A3.5; A4.5.

The recurring law is:

## 12. RC-08 - Dashboard projection/browser integration semantics are not cleanly separated from canonical product truth

`WSA-2026-041`, `042`

**Severity:** 2 MEDIUM

### Root statement

Dashboard is intended as a projection/control surface rather than a new canonical owner.

## 18. Cross-repository systemic laws derived from the graph

A6.2 extracts the following whole-system invariants for future repair/recheck.

### Law G1 - Physical and logical scope must both hold

A path/scope/ID being syntactically correct is insufficient.

Canonical operations require physical containment and trusted provenance.

### Law G2 - Final-edge authority wins

Setup-time validation does not substitute for rechecking current authority immediately before canonical write/read/external effect.

### Law G3 - Semantic uniqueness requires an atomic owner primitive

Idempotency, natural-key uniqueness, handoff and one-writer rules cannot be implemented as unprotected query-then-effect sequences.

### Law G4 - Lifecycle truth must gate action

Installed/attached/enabled/healthy/ready are not informational labels; canonical actions must derive permission from authoritative owner state.

### Law G5 - Long-lived state needs explicit retention/index/freshness design

A public-beta path expected to run for months cannot rely on indefinitely growing full-file scans or source-blind caches.

### Law G6 - Sensitive output is untrusted data

Provider/child stderr and error bodies must be minimized/redacted before persistence or display.

### Law G7 - Release truth must be generated/validated, not copied by hand

Current release identity, profile composition, requirements and acceptance state need machine-enforced synchronization.

### Law G8 - Acceptance must reach the member boundary

A component/unit/synthetic runtime gate is valuable but cannot be the sole qualification for a broader composed product claim.

### Law G9 - UI is a projection, never an accidental owner

Dashboard semantics must remain rebuildable projections of canonical owner truth.

### Law G10 - Expensive authentication work needs pre-auth admission control

Local-first does not eliminate denial-of-service/resource-exhaustion boundaries.
