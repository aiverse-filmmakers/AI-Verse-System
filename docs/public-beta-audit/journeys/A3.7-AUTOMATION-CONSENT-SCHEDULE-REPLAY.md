## 10. Occurrence identity

`automation_id + trigger_id + exact scheduled instant`.

Event/webhook invocation identity binds:

- Automation;
- trigger;

Due claim and trigger advancement occur inside one `BEGIN IMMEDIATE` transaction.

This prevents two sequential scheduler ticks from materializing different canonical occurrences for the same scheduled instant.

## 18. Owner retry/recovery semantics

Current Automations owner behavior includes:

- same stable invocation ID on retry;
- bounded attempts/backoff;
- current OS permission rechecked on every delivery attempt;
- unknown crash-recovery result is never silently replayed;
- explicit retry of an unknown delivery requires operator confirmation;
- recurrence misfires coalesce instead of replaying unbounded backlog.

The public-beta scheduler scope is one local scheduler process.

A simultaneously live second scheduler is explicitly outside current supported scope.

## 19. Event replay

For event/webhook-driven recurrence:

- source event identity is durable;
- source/type/body digest is bound;
- matching replay returns the prior canonical run;
- changed body/type/source under the same event identity fails closed.

Webhook ingress includes:

- HMAC validation;
- timestamp replay window;
- persistent receipt;
- bounded body size.

This is separate from scheduled cron occurrence identity but follows the same replay law.

## 20. Gateway concurrent invocation defect

Sequential exact wake replay is correct.

However Gateway's first-claim idempotency admission is not linearizable.

Two simultaneous first deliveries of the same invocation ID can both observe no reservation and both create a new run.

This remains:

`WSA-2026-008` - HIGH.

Therefore A3.7 cannot claim concurrent replay safety even though restart/sequential replay is accepted.

## 21. Scheduler-store ownership defect

Automations canonical state can adopt/mutate a foreign SQLite database if it is pointed at one.

Health/readiness does not fully prove the store belongs to Automations before mutation.

This remains:

`WSA-2026-026` - HIGH.

The accepted A3.7 journey uses a valid owner-created store, so the normal path succeeds, but the canonical-store boundary remains unsafe.

## 22. Legacy schedule authority conflict

It prevents a clean whole-journey verdict.

## 23. OS attachment/lifecycle divergence

Automations owner lifecycle and OS extension attachment can diverge.

Existing examples include:

- component disabled while OS registry still says enabled;
- component enabled while OS registry says disabled;
- uninstall leaving registry/bridge residue.

The retained bridge fails closed if owner readiness disappears, which limits effect authority, but lifecycle truth is still inconsistent.

This remains:

`WSA-2026-028` - MEDIUM.
