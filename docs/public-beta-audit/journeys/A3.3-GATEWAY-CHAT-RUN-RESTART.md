## 3. Client authentication and request boundary

Current Gateway:

- listens on the configured loopback boundary by default;
- requires bearer authentication for application routes;
- derives the effective principal from the verified bearer key;
- does not trust caller-supplied actor/user headers as authentication;
- bounds request body size;
- applies principal-scoped rate limiting after authentication;
- binds sessions/runs to system/workspace/principal.

A normal chat request cannot directly choose trusted owner authority fields.

## 4. Session and run binding

A run records:

- session ID;
- system ID;
- workspace ID;
- authenticated principal;
- runtime;
- bounded budgets;
- deadline;
- canonical messages;
- run status;
- event stream;
- optional Goal binding.

Existing sessions cannot be sequentially rebound to a conflicting system/principal/workspace.

The concurrent first-binding race remains existing `WSA-2026-008`.

## 5. Context assembly before runtime

For a normal turn Gateway requests bounded current owner context instead of opening sibling stores directly.

Current context may include:

- OS current context;
- capability discovery;
- bounded Connections metadata;
- Memory progressive context;
- Context Ladder derived state where appropriate.

Context is scope-bound to the run's:

- system;
- workspace;
- principal.

Cross-workspace fold/archive access fails closed.

A3.4 audits the deeper context journey separately.

## 6. Runtime boundary

The runtime receives only:

- bounded conversational context;
- `aiverse_context` for bounded deeper retrieval;
- `aiverse_action` for bounded actions.

Runtime output cannot inject trusted:

- scope;
- principal;
- system ID;
- workspace ID;
- permission;
- approval;
- consent;
- durable owner IDs;
- credentials;
- trusted provenance.

Side effects return through OS authorization/owner routing.

## 7. Run state machine

Current run states include:

- queued;
- running;
- awaiting_approval;
- resuming;
- paused;
- parked;
- paused_no_progress;
- paused_recovery_required;
- blocked;
- budget_limited;
- failed;
- canceled;

This gives the runtime an explicit durable state model instead of relying on an in-memory provider process.

## 14. In-flight restart semantics

If Gateway restarts while a run is in:

- running;
- resuming;
- waiting-tool execution state

the store recovery path marks the run:

`paused_recovery_required`.

This is intentionally conservative.

The system does not pretend it can transparently resume an arbitrary provider process that no longer exists.

That is correct runtime truth.

## 15. Completed-session post-processing

A completed run remains canonical even when optional post-completion Memory digest handoff fails.

Gateway may mark that handoff retryable and recover it after restart.

The run itself is not reopened or downgraded.

Retry uses a stable run-bound idempotency key.

This preserves separation between:

- canonical Gateway run completion;
- optional historical Memory promotion.

## 16. Idempotency and replay

Sequential reuse of the same operation ID with changed payload fails closed.

The run store persists idempotency/control records.

However first-claim concurrency is not linearizable.

Two simultaneous first claims can both observe no reservation.

This remains existing:

`WSA-2026-008` - HIGH.

A3.3 does not allocate a duplicate finding.

## 17. Pause/cancel concurrency

Authenticated pause/cancel works on the normal sequential path.

Under concurrent asynchronous execution, a stale in-memory run object can later overwrite newer persisted pause/cancel state.

This also remains:

`WSA-2026-008`.

Therefore A3.3 PASS applies to the verified sequential journey, not to adversarial concurrent control semantics.

A4.2 retains responsibility for concurrency attack execution.

## 18. Gateway lifecycle truth

Gateway lifecycle state can diverge from actual live service state because enable/disable/status do not own a real background service manager.

That remains existing:

`WSA-2026-007` - HIGH.

The Distribution acceptance explicitly starts/stops the Gateway process itself and therefore proves the chat/restart journey independently of that lifecycle-state defect.

## 20. Deep-context freshness limitation

A repeated identical deep-context request can replay stale exact-source content from the per-run cache without revalidating source version/fingerprint.

This remains:

`WSA-2026-045` - MEDIUM.

That does not prevent the basic chat/run/restart path from completing, but it affects exact evidence freshness inside long-running sessions.

A3.4 audits that context journey directly.

## 21. Restart preservation boundaries

A restart preserves:

- sessions;
- completed runs;
- run messages;
- run status;
- run events;
- Goal binding;
- idempotency metadata;
- pending optional digest retry metadata;
- fold/archive derived state where valid.

A restart does not preserve:

- the exact live provider process;
- in-flight provider execution as if nothing happened.

In-flight work is paused for recovery instead.

This is the correct boundary.
