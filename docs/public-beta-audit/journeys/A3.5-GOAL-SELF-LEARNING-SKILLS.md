## 4. Brain learning candidate gate

Brain exposes a deterministic gate:

`admit_skills_learning_candidate`

The runtime/model may suggest a candidate, but Brain decides whether it is eligible to reach Skills.

Current gate enforces:

- substantial-task requirement;
- exact trusted bound scope;
- owner must be Skills;
- only create/repair kinds;
- bounded stable candidate ID;
- safe Skill/target ID;
- evidence refs required;
- confidence threshold;
- low/medium/high risk enum;
- bounded requested capabilities/dependencies;
- no raw transcript;
- no credentials/secrets/private key/raw tool output;
- no permission grant/authorization/approval injection;
- workspace-local learning requires a workspace-bound scope.

Brain does not write Skill package bytes.

It emits a bounded Skills envelope.

## 8. Real learning flow inside four-repo acceptance

The maintained OS host acceptance uses the real Brain and real Skills owners.

It proves:

### Initial proposal route

- OS authorizes `skills.learning-candidate`;
- Brain admits a substantial safe candidate;
- real Skills receives the proposal;
- default propose mode leaves it `pending_approval`;
- exact proposal ID is bound;
- exact replay returns no duplicate effect.

### Trivial work

When `substantial_task=false`:

- Brain ignores the candidate;
- no Skills mutation occurs.

### Unsafe ID

A candidate with a path-like Skill ID such as `../escape` is rejected by Brain before Skills mutation.

### Auto learning

Learning mode is explicitly changed to `auto`.

A real safe candidate is submitted through the same OS -> Brain -> Skills route.

Result:

- Brain admits;
- Skills applies under `policy:auto`;
- a new immutable generation is activated;
- active generation equals the returned applied generation.

### Restart / later use

A fresh host object is created after learning.

The learned capability is rediscovered from the current Skills owner rather than retained in an in-process cache.

A later action reads instructions using:

- exact capability ID;
- exact generation ID;
- exact package digest.

The execution receipt binds those values.

### Quarantine

A later unsafe candidate is evaluated by the real Skills owner and remains `quarantined`.

It is not exposed as a capability.

### Rollback

The learned proposal is rolled back.

Skills active generation returns to the backup generation.

A fresh post-rollback host no longer discovers the learned capability.

This is strong owner-level adoption and rollback evidence.

## 19. Security/authority boundary result

Current learning architecture correctly prevents model self-promotion.

Runtime cannot supply trusted:

- candidate ID;
- scope;
- evidence refs;
- created-at provenance;
- task evidence;
- approval;
- permission grant;
- credentials/secrets.

Gateway/OS derive trusted context.

Brain decides cross-owner candidate eligibility.

Skills independently decides proposal security/admission and immutable promotion.

OS permission remains an outer action gate.

A learned Skill does not gain more authority merely because it was learned.

## 20. Rollback boundary result

Skills rollback is not "edit old generation in place."

Learning promotion creates a new immutable generation.

Rollback changes the active generation under compare-and-set conditions.

Old/new generations remain explicit.

A later consumer binds the exact generation/package digest.

This is the correct capability rollback model.
