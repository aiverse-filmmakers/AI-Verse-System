## 3. Semantic migration-drop product behavior

Current OS provides the `migration-drop` capability for large prior-assistant/context transfers.

It explicitly recognizes material originating from:

- ChatGPT;
- Hermes;
- Claude;
- Codex;
- notes archives;
- USER.md;
- MEMORY.md;
- SOUL.md;
- raw pasted context with no filename.

The user does not need to say "import" or name AI-Verse architecture.

The capability classifies by real-world meaning rather than filename.

## 4. Semantic routing law

The current migration contract routes:

### Stable operator identity/preferences

To the OS operator profile.

### Clear substantial clients/projects/products/areas

To OS workspace ownership.

### Durable historical facts/events/lessons

To Memory.

### Repeated current structured operational truth

To Data.

### Reusable procedures

Only to a possible later Skills candidate through normal Skills safeguards.

### Ambiguous real-world meaning

To resumable clarification.

It does not ask the user to choose internal destinations.

## 5. Foreign assistant content is not authority

SOUL/system-prompt-style content is treated as migration data.

The current migration contract explicitly distinguishes:

- real user preferences, which may be retained;
- foreign runtime identity/tool instructions, which must not become AI-Verse authority.

For example, imported text such as:

- "You are Hermes";
- "Call the Hermes memory tool";
- foreign system override instructions

cannot replace AI-Verse runtime/security/ownership rules.

Current tests prove attempted foreign runtime identity can be rejected as an operator preference.

## 6. Clarification behavior

When meaning is genuinely ambiguous:

- already-safe high-confidence material is retained;
- ambiguous material is not discarded;
- user-facing questions ask about real-world meaning;
- internal words such as workspace, Memory, Data, Skill, owner, canonical or scope are rejected in clarification questions;
- unresolved clarification state is persisted in OS migration receipts;
- `migration.pending` can resume after interruption;
- a later answer can resolve the old clarification and create newly justified owner state.

The exact current test covers:

1. raw paste with no filename;
2. stable operator identity;
3. stable communication preference;
4. ambiguous TUI relationship;
5. persisted pending clarification;
6. later answer that TUI is a current ongoing client;
7. resulting workspace route;
8. zero pending questions after resolution;
9. prior receipt marked complete.

This behavior is correct.

## 7. Raw-source handling

The migration contract intentionally avoids creating a second canonical raw archive of the imported context.

Current route:

- hashes the source;
- binds source fingerprints/evidence refs;
- stores bounded clarification evidence when needed;
- routes only admitted durable facts;
- records owner receipts;
- records `raw_source_persisted: false`.

The OS migration test verifies that the full source text and imported Memory body are not copied into the migration receipt.

This is a strong non-duplication boundary.

## 8. Replay/idempotency

Semantic import uses stable source/plan identity.

Current behavior verifies:

- identical source + identical plan replays without duplicate owner writes;
- same unchanged source with harmless classifier-plan variation replays by source identity;
- workspace/Memory/Data writes are not duplicated by that reclassification;
- clarification answer resolution is linked to the original pending question.

This is appropriate for model-assisted classification, where wording may vary while source semantics remain unchanged.

## 13. WSA-2026-047 - semantic migration-drop lacks real composed owner acceptance

**Severity:** MEDIUM  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** migration release evidence / cross-owner persistence  
**Affected repos:** `AI-Verse-OS`, `AI-Verse-Gateway`, `AI-Verse-Memory`, `AI-Verse-Data`, `ai-verse-distribution`

### Summary

Semantic migration-drop is a current user-facing migration feature.

OS and Gateway tests verify classification, clarification, source binding, owner request shape and replay, but they replace the actual owner implementations with stubs/fixtures.

No reviewed composed acceptance takes one real migration source through:

`Gateway/direct runtime -> OS migration -> real workspace owner -> real Memory -> real Data -> restart -> clarification resume -> replay verification`.

### Impact

A3's "no data loss" and end-to-end owner persistence requirement is not fully proven for semantic migration.

This is not evidence that real owner routing currently fails.

It is a release-evidence gap on a data-migration path where incorrect persistence or partial owner success would be material.

### Required closure evidence

Add a composed migration acceptance using exact admitted component refs that:

1. starts from a real AI-Verse OS root;
2. installs/attaches real Memory and Data owners;
3. imports a raw no-filename USER/MEMORY/SOUL-style context block;
4. creates a real operator profile;
5. creates a real client/project workspace;
6. writes real workspace-scoped Memory;
7. writes real structured Data;
8. verifies no full raw migration source was duplicated;
9. stops with a real pending clarification for ambiguous material;
10. survives process restart;
11. resumes `migration.pending`;
12. applies a real clarification answer;
13. verifies exact owner state after resolution;
14. replays the unchanged source and proves no duplicate owner writes;
15. injects one downstream owner rejection/failure and proves other admitted state and receipts remain truthful;
16. runs on the supported platform matrix appropriate to the admitted release candidate.

## 14. Brain standalone-to-native adoption

Brain's supported adoption path is materially stronger than a blind copy.

Current behavior:

- validates standalone Brain objects;
- rejects unsafe source object symlinks;
- stages copied native state;
- preserves source provenance;
- retires old writable source;
- activates the native destination transactionally;
- does not silently transfer strategic direction.

Brain disable/uninstall preserve canonical Brain state and are blocked while Brain owns direction until explicit handback.

The major remaining defect is destination parent containment:

`WSA-2026-009` - HIGH.

A symlinked native destination parent can escape the intended OS root/scope.

A3.2 inherits that finding.

Successful migration preserves:

## 16. Memory authority handoff failure

The final Memory authority transfer is not failure-atomic.

Current handoff order is:

1. target native `authority-handoff.json` becomes complete;
2. source `AUTHORITY.json` becomes retired;
3. legacy writer is backed up/replaced by a retirement stub.

No cross-root journal or two-phase handoff makes that sequence atomic.

If failure occurs after step 1 but before source retirement, both roots can remain writable.

This remains existing:

`WSA-2026-014` - HIGH.

The current exact-head tests cover:

- successful retirement;
- unresolved migration with no retirement.

They do not inject failure between the authority-publication steps.

This directly prevents A3.2 from receiving a clean whole-journey PASS.

## 17. Memory lifecycle authority interaction

The handoff risk is compounded by:

`WSA-2026-013` - HIGH.

Native Memory canonical writes do not enforce the full installed/attached/enabled/setup/migration-required lifecycle state.

Therefore an interrupted migration can be reported migration-required while native code can still mutate canonical state.

The combination of `WSA-2026-013` and `014` means migration recovery cannot currently rely on lifecycle status alone to preserve singular writable authority.

## 18. Memory lifecycle path risk

Memory lifecycle operations also retain:

`WSA-2026-012` - BLOCKER.

Lifecycle runtime/adapter write/remove paths do not validate every parent realpath.

A symlinked parent can redirect setup/install/uninstall writes or recursive removal outside the selected target.

This is relevant to existing-system attach/setup journeys because adoption may execute lifecycle paths against an existing tree.

A3.2 inherits the blocker rather than opening another finding.

## 19. Data import/restore/migration

Data's native migration/restore model is strong in isolation.

### User-schema migration

It:

- previews read-only first;
- binds preview digest to executor/owner/schema/current records;
- recomputes under write intent;
- requires destructive approval metadata where applicable;
- uses bounded deterministic backfills;
- commits schema/records/relations/idempotency/provenance atomically.

No arbitrary model-generated SQL migration is accepted.

### Backup/restore/import

It:

- uses consistent SQLite snapshots;
- verifies artifact identity;
- requires expected binding;
- stages before installation;
- refuses an existing canonical destination.

### Corruption/recovery

Quarantine blocks canonical writes.

Recovery diagnoses original source without silently replacing it and stages verified recovery separately.

The separate public-client trusted-scope provenance defect remains `WSA-2026-020`, but native owner flows are stronger.

## 20. Distribution reconcile for existing installs

`aiverse start` does not silently transform arbitrary existing installations.

For a previously setup Agent with `setup-required`, safe reconcile admits only one exact automatic action:

- locked Brain revision;
- Brain attach;
- Brain init;
- no registry lock;
- no migration-required state;
- no unknown automatic action.

Anything else stops for explicit review.

This preserves migration/adoption authority with the owner instead of turning Distribution into a generic recovery engine.

## 21. Existing folder adoption and no silent profile switch

Distribution also refuses to silently:

- move an existing installation root;
- switch an existing profile;
- change release set;
- reinterpret a Core lock as Agent.

This is appropriate for existing-system safety.

Cross-release migrations are not currently admitted, so A3.2 does not claim unproven version migration behavior.

## 22. No-data-loss assessment

### Semantic migration

High-confidence facts and pending ambiguity are designed to survive without full raw duplication.

However, real composed owner persistence has not been proven end to end under `WSA-2026-047`.

### Brain

State preservation/adoption semantics are strong on normal paths, with path-boundary risk under `WSA-2026-009`.

### Memory

Normal successful copy is provenance-preserving, but interrupted authority transfer can produce dual writable stores under `WSA-2026-014`.

### Data

Native migration/restore is staged and atomic/refusal-oriented.

### Distribution

Existing install reconcile is deliberately narrow and fail-closed.

Therefore A3.2 cannot certify the global "no data loss / singular authority after migration" requirement.
