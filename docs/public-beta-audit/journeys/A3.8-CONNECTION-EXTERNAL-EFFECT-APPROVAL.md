## 3. Canonical external-effect ownership

Connections is the canonical owner of:

- connection identity/configuration;
- system/workspace connection scope;
- credential handles/vault state;
- provider adapter state;
- capability admission;
- connection approval;
- per-action approval checks;
- idempotency reservations;
- external-effect receipts;
- final provider-edge enforcement.

Connections does not own:

- Gateway run/session truth;
- Brain strategy;
- OS permissions;
- Automations schedule truth;
- Data canonical external records;
- Token normalized cost truth.

External provider data remains externally canonical unless another explicit sync/import contract is used.

## 4. Credential boundary

Connections uses opaque credential handles.

The master key comes from:

`AIVERSE_CONNECTIONS_MASTER_KEY`

and is not stored in the Connections registry.

Provider adapters resolve secret material only at the provider edge.

Ordinary list/receipt paths are designed not to persist raw credential values.

The core integration test verifies a Generic API call using:

- credential handle `vault:api-token`;
- real vault secret;
- real provider request;
- registry/receipt inspection.

It asserts the raw secret is absent from:

- registry;
- receipts.

This is the correct credential ownership boundary on the normal path.

## 5. Connection state and verification

A connection separates:

- registration;
- verification;
- capability admission;
- connection approval;
- per-action approval;
- execution.

Verification is not approval.

Capability admission is not approval.

Connection approval is not a permanent write/admin bypass.

This separation is important for MCP capability drift and external provider changes.

## 6. Capability admission and connection approval

MCP verification discovers provider/tool metadata.

The current integration test verifies:

1. MCP bearer credential is injected by the trusted adapter;
2. protocol version is correct;
3. server identity/instruction signals are recorded;
4. one discovered capability is explicitly admitted;
5. the connection is explicitly approved;
6. that admitted capability can execute.

If later MCP verification changes the capability surface, prior approval is invalidated.

This prevents stale connection approval from silently authorizing a changed provider contract.

## 7. Per-action approval

Write/admin risk requires explicit per-action approval during execution.

Connections accepts trusted delegated capability/approval provenance from an upstream host boundary.

The component itself does not authenticate that upstream caller.

That is an intentional seam assumption, not proof of upstream authentication.

Because Connections is outside the current Agent release, there is no current supported end-user Agent journey whose correctness depends on that uncomposed inbound seam.

A future Full-profile path must prove that seam before promotion.

## 8. System/workspace checks

Normal execution verifies:

- request system ID equals connection system ID;
- workspace is allowed by the connection;
- requested capability is admitted;
- delegated capabilities include the requested capability;
- connection is enabled/authorized;
- required approval is present.

Repo-local integration tests exercise wrong-system and wrong-workspace rejection.

The installation-level system identity defect remains separately open as `WSA-2026-030`.

## 9. Final-edge revocation recheck

The normal final provider edge reloads the current connection and rechecks connection/capability authority immediately before adapter execution.

The core integration test injects:

`beforeFinalEdge -> revoke(connection)`

and requires execution to fail.

This proves connection-level revocation is not only checked during planning.

However the complete authority intersection is not re-evaluated there. See section 16.

## 10. Generic API provider path

Generic API connections define:

- allowed base origin;
- allowed methods;
- admitted path prefixes;
- credential mode;
- health probe;
- risk/limits.

The trusted adapter adds credential headers only after policy checks.

Private/reserved/local network targets are blocked by default unless explicitly allowed.

A limits integration test verifies private-network rejection by default.

## 11. MCP provider path

Frozen Connections targets stateless HTTP MCP.

The MCP integration test uses a real local HTTP test provider and verifies:

- bearer injection;
- MCP protocol version;
- provider method envelope;
- capability discovery;
- capability admission;
- connection approval;
- tool execution;
- later capability change invalidates approval.

This is meaningful standalone provider-path evidence, even though the hosted workflow did not execute it at the frozen head.

## 12. Idempotency reservation

When an idempotency key is supplied, Connections creates an append-only pending reservation before the provider request.

The integration test verifies:

1. first request reserves the key;
2. concurrent duplicate with the same connection/capability/key is rejected as `IDEMPOTENCY_IN_PROGRESS`;
3. first request completes;
4. later exact replay returns the completed receipt;
5. provider side effect is not re-executed.

This is strong same-key duplicate-side-effect prevention on the sequential/concurrent duplicate path.

## 13. Receipts

Terminal success/provider-error results create external-effect receipts.

Receipts bind effect identity/provenance without becoming credential stores.

Completed same-key receipts are replayed instead of re-executing the provider call.

A pending reservation can remain stuck after crash/pre-provider failure because there is no pending-reservation recovery protocol.

That limitation fails closed and does not itself duplicate an external effect.

A1.10 therefore treated it as a recovery limitation rather than a standalone safety finding.

## 14. Rate/call budgets

Connections checks configured rate/call budgets before provider execution.

Repo-local limits tests verify:

- attempted calls count toward the budget;
- the next call is blocked once the limit is exhausted.

However concurrent different idempotency keys can independently observe the same remaining budget before either has committed its attempted effect accounting.

The final provider edge does not atomically reserve/recheck that budget.

This is existing `WSA-2026-032`.

## 15. Current component lifecycle interaction

Connection-level enabled/revoked state is reloaded at the final edge.

Component-level lifecycle state is not.

A concurrent component disable/uninstall after planning can therefore fail to fence an already-planned provider call.

This is also existing `WSA-2026-032`.

## 16. WSA-2026-032 final-edge authority defect

The documented authority law requires final-edge recomputation of:

- component readiness;
- connection state;
- capability state;
- workspace/system scope;
- per-action approval;
- rate/call budget.

Implementation only rechecks the connection/capability side at the final edge.

Therefore:

- component lifecycle can change after planning without fencing the effect;
- concurrent different-key calls can exceed a shared remaining budget.

This directly affects A3.8 and prevents a clean journey verdict.

## 17. WSA-2026-030 installation system-binding defect

Setup records one installation system ID.

Connection registration can still create a connection for another system ID.

Execution then compares:

`request system -> connection system`

but does not enforce:

`connection/request system -> lifecycle installation system`.

One Connections home can therefore execute external authority for a different system than the installation claims to belong to.

This remains existing `WSA-2026-030`.

## 18. WSA-2026-031 credential-origin defect

Initial MCP registration prevents one bearer credential handle from being reused across different MCP origins.

Reauth does not repeat that rule.

An existing connection for origin B can be reauthenticated with a handle already used by origin A.

The next verification can resolve and transmit that bearer credential to origin B.

This remains existing `WSA-2026-031` and directly affects the credential boundary of A3.8.

## 19. WSA-2026-033 normalized-path authorization defect

Generic API path-prefix policy checks the raw caller path before WHATWG URL normalization.

Dot-segment/encoded path forms can pass the allowed prefix and normalize outside that prefix while staying on the same origin.

The trusted adapter can then attach the connection credential to an unintended same-origin endpoint.

This remains existing `WSA-2026-033`.

## 23. Failure behavior

Current effect execution is conservative in several ways:

- unsupported/private target blocked before provider edge;
- missing capability/approval fails closed;
- connection revocation at final edge fails closed;
- concurrent duplicate same-key effect is blocked;
- completed receipt replays instead of re-executing;
- provider error becomes a terminal receipt;
- pending crash uncertainty does not auto-retry.

These controls reduce duplicate external-effect risk.

They do not repair the known system/origin/path/final-budget defects.

## 24. Retry behavior

Exact terminal same-key replay returns the prior receipt.

Pending/unknown reservation does not automatically execute again.

There is no broad "retry everything after restart" behavior.

Operator recovery of stuck pending reservations remains a limitation.

A future composed path should prove bounded retry and explicit recovery behavior at the upstream host level.

## 25. External data trust

Provider output is labeled:

`untrusted_external`.

A provider response does not become canonical Data/Memory truth merely because Connections fetched it.

Any future sync/import into Data/Memory must pass that owner’s admission contract.

This preserves canonical owner boundaries.
