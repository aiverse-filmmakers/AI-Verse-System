## 3. Threat model boundary

The current public-beta model is single-operator and local/VPS oriented.

A4.4 therefore distinguishes:

1. legitimate operator visibility across the operator's own local system;
2. workspace/system isolation that the architecture explicitly promises;
3. transport authentication boundaries;
4. receipt/log persistence that can duplicate secrets or private provider content into new stores;
5. hidden-resource existence or provenance leakage across an unauthorized scope.

A local operator being able to inspect their own owner data is not classified as a privacy defect by itself.

A read surface that bypasses a documented scope/system/authentication fence is material.

## 4. Gateway run/session visibility

Gateway application routes, except the public health path, require bearer authentication.

Run reads, event streaming and diagnostics first resolve the run through the authenticated principal ownership check.

Session creation binds:

- system ID;
- workspace ID;
- authenticated principal.

An existing session ID cannot be reused under a mismatched system or principal.

A workspace is explicitly validated before a new run is created.

Gateway audit receipts store a digest of the request, not the raw prompt body.

### A4.4 attack result

No new Gateway privacy root cause was found in the reviewed run/session/event path.

Existing relevant Gateway defects remain:

- `WSA-2026-008`: concurrency can race first session/idempotency binding;
- `WSA-2026-045`: deep-context freshness/provenance caching.

Neither creates a separate newly proven disclosure path under A4.4.

## 5. Memory workspace visibility

Memory normal retrieval derives visible scopes through `allowed_scopes(..., all_workspaces=False)`.

Current native rules are:

- operator request -> operator scope;
- workspace request -> that workspace plus operator scope;
- no normal request -> operator scope;
- broad all-workspace retrieval is a separate privileged host surface and is not used by Gateway Context Ladder.

This matches the current single-operator Memory model.

## 6. Context Ladder exact-source descent resists cross-scope probing

Progressive recall source depth does not trust an evidence reference as sufficient authority.

Before exact-source lookup it:

1. normalizes the evidence scope;
2. recomputes currently allowed scopes;
3. rejects the request when the evidence scope is not visible;
4. validates record scope again after lookup;
5. validates canonical path and source version;
6. fails closed on containment/version drift.

A caller cannot use a workspace-A evidence reference to descend into exact source while requesting workspace B.

## 7. Memory relationship/provenance projection remains scope fenced

Memory relationship projection is rebuildable derived state.

`list_relationships`:

- recomputes visible scopes with `all_workspaces=False`;
- applies an explicit scope predicate;
- returns an empty result rather than falling back to an unscoped query when visibility is empty.

Canonical atomic-to-atomic and atomic-to-session-digest edges are emitted only when both canonical ends resolve in the same authorized scope.

Progressive relationship-neighbor expansion consumes that scope-filtered relationship surface.

### A4.4 attack result

No new cross-workspace Memory/provenance leak was found in reviewed Context Ladder paths.

## 9. Token ordinary projections and exports

Token read authorization establishes an immutable scope floor before query execution.

A conflicting read filter outside that floor fails closed.

Default JSON/Gateway/MCP projections remove:

- raw source record IDs;
- source fingerprints;
- provider external-charge IDs.

CSV export does not include those provenance identifiers.

Raw provenance IDs require explicit opt-in.

Canonical usage records do not contain prompt or response text.

### A4.4 attack result

No new Token prompt/content/provenance disclosure was found.

The monetary-authority defect `WSA-2026-024` remains correctness/authority related, not a newly distinct privacy finding.

## 10. Brain action receipts

Brain action ledgers deliberately avoid persisting full action parameters or full provider response bodies.

They retain:

- request fingerprint;
- action class;
- scope;
- operation;
- receipt identity;
- minimal effect/result status;
- bounded execution binding where applicable.

Host exceptions are reduced to exception type in the durable ledger.

The returned in-process `ActionOutcome.result` may contain the current action result for the active caller, but replay storage is intentionally minimal.

### A4.4 attack result

No new durable Brain receipt leakage was found.

## 11. Automations wake and receipt privacy

Automations intentionally stores the configured wake payload because it is canonical schedule definition state.

Run rows also retain the exact bounded wake body necessary for replay/audit.

The success path stores the downstream owner receipt in `wake_receipts`, while the ordinary run receipt contains only:

- downstream owner kind;
- downstream receipt digest.

This duplicates bounded downstream receipt evidence into the Automations owner store.

Reviewed current owner adapters do not create a newly proven unauthorized read path to that table:

- Automations exposes no remote receipt-list service;
- local CLI access is operator-local;
- Gateway automation invoke returns compact run/invocation state;
- normal run list access is local owner tooling.

A4.4 therefore records this as retained privacy surface, not a standalone finding.

A future hosted/multi-principal Automations read API would need a separate authorization and minimization review.

Dashboard event reads use workspace-filtered event queries, and live dashboard event streaming filters events by workspace before delivery.

The current transport bearer is system/operator level rather than a per-workspace user role. That is consistent with the current single-operator model.

## 15. Connections positive receipt controls

Connections has several strong minimization controls:

- registry/list surfaces do not return raw credential secrets;
- credentials are stored behind opaque handles;
- Generic API caller-supplied Authorization/cookie/API-key headers are rejected;
- successful/provider-error execution receipts store only compact result summary rather than raw provider response;
- normal Generic API integration tests prove a bearer value does not appear in registry or receipt files;
- response headers exclude Authorization and Set-Cookie;
- redirect following is disabled.

These controls make the newly identified MCP failure path narrower and easier to isolate.

## 16. New attack: provider-controlled MCP error text crosses into trusted local receipt/log surfaces

The MCP adapter accepts JSON-RPC error responses from the external provider.

When `payload.error` is present it raises:

`MCP_RPC_ERROR`

using:

`payload.error.message`

as the exception message.

It also attaches the complete remote error object as exception details:

`{ rpc: payload.error }`

No redaction/minimization is applied to either before they leave the adapter.

## 17. Durable receipt leak

Connections `execute()` catches that provider exception and appends a terminal failure receipt containing:

`errorMessage: err.message`

The receipt is append-only local evidence.

Therefore arbitrary text selected by the remote MCP server is copied into durable local Connections state.

A malicious or compromised MCP server already receives the configured bearer credential at the HTTP edge.

It can deliberately echo:

- that bearer value;
- private tool/provider data;
- credential-shaped values;
- sensitive upstream error context

inside `payload.error.message`.

Connections will then persist that text outside the credential vault in `receipts.ndjson`.

This defeats the component's otherwise strong opaque-handle/secret-at-rest boundary.

## 18. CLI/log leak

The Connections CLI catches `ConnectionsError` and serializes:

- code;
- message;
- details.

For MCP RPC errors, `details.rpc` is the provider-controlled complete JSON-RPC error object.

Therefore provider-controlled error data can also reach terminal/JSON output and any captured logs, independently of the durable receipt message field.

No current redaction function is applied at that boundary.

## 19. WSA-2026-057 - MCP provider errors can persist or print unredacted sensitive content through Connections receipts and CLI diagnostics

**Severity:** MEDIUM  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** provider-error diagnostics / receipt minimization / secret-at-rest boundary  
**Affected repo:** `AI-Verse-Connections`  
**Affected journeys:** external MCP effect failure; diagnostics/support; receipt inspection

### Summary

Connections normally keeps credentials behind opaque handles and minimizes terminal effect receipts.

However an MCP JSON-RPC error is converted into a trusted local exception using the provider-controlled error message and full error object without sanitization.

The execution failure path persists `err.message` in the append-only receipt, and CLI error handling can emit the full exception details.

### Evidence

`src/providers/mcp.js`:

- reads arbitrary remote JSON;
- when `payload.error` exists, raises `MCP_RPC_ERROR`;
- uses `payload.error.message` directly as exception text;
- attaches the complete `payload.error` as `details.rpc`.

`src/service-execute.js`:

- catches the provider error;
- writes `errorMessage: err.message` into the durable failure receipt;
- performs no sanitization/redaction before append.

`src/cli.js`:

- serializes ConnectionsError `message` and `details`;
- therefore can print the remote RPC error object.

Existing tests prove the normal Generic API bearer is absent from receipts, but no MCP regression was found that injects secret-like provider error text and proves it is redacted.

### Impact

A malicious or compromised MCP provider can cause credential-like or private provider content to be:

- persisted outside the credential vault in append-only Connections receipts;
- emitted in terminal/JSON diagnostics;
- copied into captured support/log output.

The provider already has access to the bearer presented to it, so this does not grant the provider a new credential.

The defect broadens local persistence and downstream log exposure, which is why severity is MEDIUM rather than HIGH.

### Required closure evidence

After repair authorization:

1. define a provider-error sanitization/minimization boundary before durable receipt or CLI output;
2. never persist raw external RPC error messages when they can contain credentials/private content;
3. store a stable bounded error code/category and safe summary instead;
4. redact credential-shaped values in user-visible diagnostic output;
5. keep raw provider details only if an explicitly protected debug channel is designed and authorized;
6. add deterministic MCP tests where the server echoes the actual bearer in error message/data;
7. prove the bearer is absent from registry, receipts, CLI JSON/plain output and support artifacts.
