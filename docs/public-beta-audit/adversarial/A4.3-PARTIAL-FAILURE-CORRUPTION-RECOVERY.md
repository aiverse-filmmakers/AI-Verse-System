## 1. Adversarial scope

A4.3 attempts to falsify failure and recovery assumptions across:

- process death between read, effect and receipt publication;
- partially completed multi-owner operations;
- interrupted lifecycle setup/update/uninstall;
- stale locks after process death;
- corrupted canonical or receipt state;
- unknown external-effect outcomes;
- rollback after partial work;
- missing owner/dependency paths;
- crash recovery and replay;
- safe degradation and health truth after corruption.

This task does not repair product repositories.

## 3. Existing failure-atomicity findings carried forward

A4.3 re-attaches existing root causes instead of opening duplicates.

### Gateway lifecycle partial publication

`WSA-2026-007` HIGH remains open.

Gateway setup writes host/config state before host `describe` proves readiness. Failed setup can therefore leave structurally valid configuration that later status can call ready. Disable/uninstall also do not coordinate one authoritative live process state.

This is already the canonical Gateway setup/lifecycle recovery finding.

### Memory cross-root authority handoff

`WSA-2026-014` HIGH remains open.

Standalone-to-native migration publishes target handoff completion before source retirement is durably proven. There is no cross-root handoff journal or two-phase authority transfer.

This is already the canonical Memory partial-failure finding.

### Skills lifecycle serialization

`WSA-2026-017` HIGH remains open.

Skills does recover old lock files by age, but recovery does not verify holder liveness. This creates overlap risk for long-running live operations. A crashed holder eventually becomes recoverable, so A4.3 does not open a second crashed-lock finding for Skills.

### Token pricing batch publication

`WSA-2026-025` MEDIUM remains open.

A validated pricing refresh publishes immutable snapshot files sequentially. A later failure can leave an earlier subset visible while the refresh is reported failed.

This is already the canonical Token failed-refresh atomicity finding.

### Automations canonical database ownership

`WSA-2026-026` HIGH remains open.

Automations initialization can execute schema creation/alteration and stamp schema metadata on an existing SQLite path without first proving exact store ownership/format identity. Foreign or incompatible state can therefore be modified before failure.

This remains the canonical Automations corruption/ownership finding.

### Distribution owner-effect / receipt split

`WSA-2026-034` HIGH remains open.

Distribution owner lifecycle effects and Distribution receipt publication are not one durable semantic transaction. The existing finding was discovered through concurrent stale writers, but the same root boundary is also the relevant crash window: owner mutation can complete before the receipt commit.

No duplicate crash-only finding is opened.

### OS semantic migration source reservation

`WSA-2026-052` HIGH remains open.

Migration subactions use deterministic plan-derived idempotency keys, so same-plan retry after many partial failures is comparatively strong. However the source-level receipt is published only after all subactions. A crash before that final receipt means a later differently classified plan has no durable same-source reservation to replay against.

That is the same root source-admission problem already captured by WSA-052.

## 4. Gateway recovery result

Gateway has strong run-level restart behavior:

- durable run state exists;
- interrupted `running`, `resuming` and waiting-tool states become `paused_recovery_required`;
- recovery does not pretend that an unknown provider/tool effect safely resumed;
- completed-run Memory digest handoff can retry without reopening the canonical completed run.

The major failure remains lifecycle publication under WSA-007.

No new Gateway A4.3 root cause was found.

## 5. Memory recovery result

Memory same-root canonical mutation is one of the strongest reviewed recovery implementations:

- cross-process canonical mutation lock;
- atomic temp-file replacement;
- supersession journal written before paired canonical writes;
- incomplete journal replay under the canonical lock;
- effect receipts written under that lock;
- changed effect-ID payload reuse fails closed;
- derived SQLite failure can rebuild from canonical files.

The failure boundary is the cross-root authority transfer already captured by WSA-014.

No new Memory A4.3 finding is opened.

## 6. Data corruption and recovery result

Data explicitly treats corruption as a first-class state.

Reviewed behavior includes:

- SQLite physical integrity inspection;
- semantic/storage error classification;
- durable quarantine markers;
- quarantine blocking canonical writes;
- recovery inspection against the original source without silently repairing it;
- staged recovery into a different physical database;
- exact trusted workspace binding required for the recovery destination;
- staged destination health verification before it is considered usable;
- transactional mutation/provenance/idempotency behavior.

A4.3 found no new Data recovery root cause.

## 7. Automations crash uncertainty result

Automations explicitly models unknown delivery after a scheduler/process crash.

Current behavior:

- due occurrence claim and trigger advancement use `BEGIN IMMEDIATE`;
- invocation IDs are deterministic;
- wake/event receipts are durable;
- nonterminal work owned by an ended process becomes `unknown`;
- unknown delivery is not automatically replayed;
- explicit retry requires owner-idempotency confirmation;
- current authority and definition fences are rechecked before retry.

That is the correct fail-closed direction for an external-effect scheduler.

Automations still carries WSA-026 for canonical-store ownership/format identity.

No new A4.3 Automations finding is opened.

## 8. Multiple Bots recovery result

Multiple Bots distinguishes replay-safe and unsafe stale execution.

Reviewed controls include:

- stale retry-safe execution can be requeued;
- unsafe stale execution dead-letters;
- live heartbeat/lease behavior prevents ordinary live work from being reclaimed as stale;
- terminal Task state can be reconciled against stale execution state;
- recovery uses atomic store mutations with preconditions;
- operator retry remains an explicit controlled path;
- remote lease recovery revalidates local canonical authority.

Existing workspace/operator authority findings remain separate.

No new Multiple Bots A4.3 finding is opened.

## 9. Skills immutable-generation recovery result

Skills lifecycle uses immutable generations and an atomically replaced active-generation pointer.

Current design means a failed stage/update normally leaves the prior active generation available rather than partially rewriting it.

Rollback verifies the selected generation before pointer replacement.

Uninstall/deactivation retains immutable generations for recovery.

The existing WSA-017 live-holder stale-lock defect remains the material serialization problem.

No new Skills A4.3 finding is opened.

## 10. Token recovery result

Token canonical usage ingest uses SQLite transactions for event, correlation and checkpoint publication.

Doctor is intentionally read-only and does not silently repair corrupt ledger/pricing state.

The material partial-publication weakness remains the already-proven pricing batch defect WSA-025.

No duplicate Token finding is opened.

## 11. Distribution recovery result

Current Distribution install is resumable only for the same locked selection and writes incremental receipts as components complete.

Individual receipt files use temp file, flush, fsync and replace.

Current changed cross-release transitions remain fail-closed/not admitted, which bounds the most complex multi-component rollback problem for the present profile.

However owner lifecycle action and Distribution receipt commit remain separate durability boundaries. A process death after owner uninstall/setup/update but before receipt publication can leave the Distribution view stale.

That is the same root problem as WSA-034 and is carried forward there rather than duplicated.

## 12. OS semantic migration partial-failure result

The migration import path performs owner subactions with deterministic keys derived from the import key:

- profile;
- workspace;
- Memory;
- Data.

If a process ends after some owner subactions but before the final migration receipt, an exact same-plan retry can normally replay those owner-level idempotency boundaries.

The final source/plan receipt itself is still late.

Therefore:

- same-plan crash recovery is materially better than an unkeyed multi-owner write;
- changed-plan or concurrent same-source recovery still lacks a source-level durable reservation before owner effects.

That remains WSA-052.

No duplicate A4.3 OS finding is opened.

## 13. Connections state lock has no crash recovery

Connections serializes lifecycle/registry/receipt critical sections with:

`fs.mkdir(<home>/.write.lock)`

Lock release occurs only in the `finally` block of the owning process.

The lock contains no:

- holder PID/token metadata;
- boot/process identity;
- heartbeat;
- timestamp used for stale recovery;
- liveness check;
- stale-lock reclamation path.

If the process exits or is killed after creating the lock directory and before the `finally` removal, the directory remains.

Every later `withLock` caller sees `EEXIST`, waits, then fails with `STATE_LOCK_TIMEOUT`.

There is no doctor check or documented reconcile command for this state.

This opens WSA-2026-054.

## 14. WSA-2026-054 - Connections crash can orphan the global write lock and indefinitely wedge canonical mutations

**Severity:** HIGH  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** crash recovery / state-lock ownership / external-effect receipt safety  
**Affected repo:** `AI-Verse-Connections`

### Summary

Connections uses a persistent directory as its global state lock but has no crashed-holder recovery protocol.

A process death while the lock is held leaves `.write.lock` present indefinitely.

Subsequent lifecycle, registry, idempotency and terminal-receipt mutations time out rather than recover.

### Evidence

`src/state-store.js`:

- `withLock` creates `.write.lock` with `fs.mkdir`;
- existing lock handling only sleeps until timeout;
- no stale/liveness metadata is read;
- cleanup only occurs in the owning process's `finally`;
- no recovery API exists.

`src/service-lifecycle.js`:

- status/doctor do not inspect or recover `.write.lock`.

`src/service-execute.js`:

- idempotency reservation and terminal receipt publication require `withLock`;
- write requests are not required to supply an idempotency key.

### Impact

After one crash in a lock critical section:

- future state mutations can remain unavailable until manual filesystem intervention;
- doctor can still report normal structural/runtime state because it does not test the lock;
- a later request without an idempotency key can reach an external provider and then fail when terminal receipt publication hits the orphaned lock, creating effect-without-durable-receipt risk.

This is a major lifecycle/reliability failure around an external-effect owner.

### Required closure evidence

After repair authorization:

1. store holder identity and lock generation metadata;
2. distinguish live holder from dead/crashed holder;
3. support deterministic stale/crashed-holder recovery;
4. make terminal receipt publication safe when recovery is needed;
5. expose lock health through doctor;
6. add process-death fault tests during registry mutation, reservation and terminal receipt publication;
7. prove live holders are never stolen.

## 15. Connections idempotency reservation has no unknown-effect recovery state

For requests carrying an idempotency key, Connections writes a durable receipt:

`outcome: "pending"`

before the final provider edge.

That is the correct first step for duplicate suppression.

However the pending receipt is initialized with:

`attemptedExternal: false`

and it is never transitioned before the provider call.

Only after the provider returns does Connections append a terminal:

- `success`;
- `provider-error`;
- or caught `failure`.

A process death after provider execution starts but before the terminal append leaves only the original pending receipt.

On restart:

- the same idempotency key always returns `IDEMPOTENCY_IN_PROGRESS`;
- there is no age/liveness/recovery state;
- there is no explicit operator recovery command;
- the durable receipt still says `attemptedExternal:false` even though the effect may have reached the provider.

This opens WSA-2026-055.

## 16. WSA-2026-055 - Connections crash after reservation can leave an external effect permanently unknown under a pending idempotency key

**Severity:** MEDIUM  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** external-effect idempotency / crash uncertainty / recovery  
**Affected repo:** `AI-Verse-Connections`

### Summary

Connections has a durable pre-effect pending reservation but no crash transition from pending to an explicit unknown-effect state.

A crash after the external call begins can leave the key permanently pending.

### Evidence

`src/service-execute.js`:

- pending reservation is persisted before the provider edge;
- `attemptedExternal` is initially false;
- provider execution happens later and outside the reservation critical section;
- terminal receipt is appended only after provider return/error;
- replay treats latest pending as indefinitely in progress.

No recovery path for pending reservations was found in lifecycle, CLI or tests.

### Impact

The same key cannot be safely retried or explicitly reconciled.

The durable state cannot distinguish:

- crash before provider attempt;
- crash during provider attempt;
- provider effect succeeded but receipt publication never happened.

This is intentionally fail-closed against same-key duplication, so severity is MEDIUM rather than HIGH.

It also interacts with existing WSA-032 because usage budgets count only receipts where `attemptedExternal === true`. An unknown post-effect crash can therefore remain absent from the counted budget until a stronger recovery protocol exists.

### Required closure evidence

After repair authorization:

1. persist an explicit provider-edge/unknown-effect state before or at the external attempt boundary;
2. preserve one stable reservation identity;
3. on restart, classify abandoned pending reservations deterministically;
4. require explicit reconciliation or provider-supported idempotent replay for unknown effects;
5. never claim `attemptedExternal:false` after the edge may have been crossed;
6. integrate recovered/unknown attempts into usage-budget semantics;
7. add fault injection before provider call, during provider call, after provider return and before terminal receipt append.

## 17. Connections receipt-log corruption is not recoverable or reflected in doctor

Connections receipts are stored as append-only NDJSON.

`readReceipts()`:

1. reads the full file;
2. splits on newlines;
3. calls `JSON.parse` on every non-empty line.

One malformed or truncated line therefore makes the complete receipt read fail.

Receipt reads are on the execution path before:

- budget checks;
- idempotency reservation/replay logic.

Connections doctor does not read or validate the receipt log.

Therefore a corrupted receipt line can make execution fail while status/doctor can continue to describe the component as ready/healthy from lifecycle/registry state.

No quarantine, last-good-prefix, repair, export/rebuild or corruption acknowledgement path was found.

This opens WSA-2026-056.

## 18. WSA-2026-056 - Connections receipt-log corruption can disable execution while health checks remain unaware

**Severity:** MEDIUM  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** canonical receipt corruption / health truth / recovery  
**Affected repo:** `AI-Verse-Connections`

### Summary

The append-only execution receipt log is parsed as one all-or-nothing NDJSON document.

A single malformed line makes the entire receipt history unreadable.

Execution depends on that history, while doctor does not validate it.

### Evidence

`src/state-store.js`:

- `readReceipts` maps every non-empty line through `JSON.parse`;
- no malformed-line quarantine or partial-prefix recovery exists.

`src/service-execute.js`:

- every execution loads receipts before budget checks;
- idempotency logic also depends on receipt history.

`src/service-lifecycle.js`:

- doctor validates lifecycle, registry, credentials and last live verification;
- it does not parse the receipt log.

No receipt-corruption recovery test or command was found in the frozen repository.

### Impact

A corrupted receipt log can:

- block external execution;
- make idempotency/budget evidence unavailable;
- leave health output unaware of the actual execution blocker.

The behavior fails closed rather than silently discarding history, which bounds severity to MEDIUM.

### Required closure evidence

After repair authorization:

1. define a durable receipt-store format identity and corruption protocol;
2. detect corruption in doctor;
3. preserve valid evidence rather than silently truncating it;
4. provide quarantine/recovery or rebuild only from trustworthy evidence;
5. prove malformed/truncated tail handling cannot erase prior effect truth;
6. add deterministic receipt corruption tests.
