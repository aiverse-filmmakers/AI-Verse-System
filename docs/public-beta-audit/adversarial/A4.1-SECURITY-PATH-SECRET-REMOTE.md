## 6. Gateway remote binding itself is fail-closed

Gateway server startup recognizes loopback only as:

- `127.0.0.1`;
- `localhost`;
- `::1`.

Any other bind requires both:

- `allow_remote=true`;
- `behind_tls_proxy=true`.

Application routes except `GET /health` require bearer authentication.

Browser-origin requests require an explicit allowed Origin.

Therefore no new "accidental non-loopback bind" finding is opened.

## 7. New attack: unauthenticated Gateway CPU exhaustion

Gateway request order is:

1. parse URL;
2. minimal public health special case;
3. Origin check;
4. bearer verification;
5. authenticated-principal rate limiter;
6. application route.

Bearer verification uses synchronous Node:

`scryptSync()`

for each configured bearer record until a match is found.

The only Gateway request limiter is keyed by the authenticated principal and is executed **after** bearer verification.

There is no:

- pre-auth connection/IP rate limiter;
- cheap rejection budget before scrypt;
- asynchronous/off-thread password verification boundary;
- invalid-bearer request budget.

Therefore an unauthenticated caller can repeatedly send syntactically valid invalid Bearer values and force synchronous scrypt work while never reaching the limiter.

Because scrypt runs synchronously on the Node event-loop thread, enough concurrent/rapid invalid requests can starve legitimate Gateway work.

Default loopback binding reduces exposure.

However non-loopback Gateway operation is explicitly supported when placed behind a TLS proxy, and the Gateway contract does not require that proxy to provide rate limiting.

This opens `WSA-2026-050`.

## 8. WSA-2026-050 - invalid bearer requests can exhaust Gateway CPU before rate limiting

**Severity:** MEDIUM  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** authentication availability / pre-auth resource exhaustion  
**Affected repo:** `AI-Verse-Gateway`

### Evidence

`src/server.mjs`:

- calls `bearer(req,...)`;
- only afterward calls `limiter.take(identity.principal)`.

`src/auth.mjs`:

- invalid bearer verification calls synchronous `scryptSync`;
- may repeat across configured auth records.

No pre-auth limiter is present in the reviewed request path.

No negative test for invalid-bearer request flooding was found.

### Impact

A local untrusted process, or a network client when supported remote mode is enabled, can consume the Gateway event loop with unauthenticated scrypt work and degrade/deny service to authenticated users and automation wakes.

The issue does not bypass authentication or disclose a credential.

### Required closure evidence

- add a bounded pre-auth limiter keyed to remote endpoint/IP/connection class;
- keep credential verification timing-safe;
- avoid unbounded synchronous KDF work on the request event loop;
- define trusted-proxy client-address semantics if remote mode is supported;
- prove invalid-bearer flood does not starve authenticated requests;
- run loopback and supported remote/proxy negative tests.

## 9. Connections private-network guard

Connections attempts to prevent SSRF/private-network effects.

`assertNetworkTargetAllowed()`:

1. parses the target;
2. rejects non-HTTPS when private-network access is not enabled;
3. rejects literal private/reserved IPs;
4. calls:
   `dns.lookup(host, { all:true, verbatim:true })`;
5. rejects if any resolved address is private.

This is a strong first-stage control.

However it does not pin the checked address to the actual connection used by the HTTP client.

## 10. New attack: DNS rebinding at credential-bearing provider fetch

Common Connections network flow is:

`assertNetworkTargetAllowed(url) -> fetch(url)`.

These are two independent DNS-resolution moments.

The code does not:

- retain the approved DNS address set;
- connect to a pinned approved IP;
- install a custom dispatcher/resolver constrained to that approved set;
- re-check the actual connected remote address after socket creation.

For credential-bearing provider adapters, credentials are resolved and attached before `boundedFetch` invokes normal `fetch()`.

### Generic API

`authHeaders()` resolves the vault secret and attaches:

- `Authorization: Bearer <secret>`, or
- configured trusted credential header.

Then `boundedFetch` performs the first private-network DNS check, followed by normal `fetch`.

### MCP

MCP similarly resolves the bearer handle and passes an Authorization header into the same `boundedFetch`.

A hostname controlled by an attacker can therefore:

1. resolve publicly during `dns.lookup`, passing the private-network check;
2. change DNS answer before/during the subsequent `fetch`;
3. resolve to a private/reserved target for the actual socket;
4. receive a trusted connection credential and/or trigger an internal network request.

This is the DNS rebinding class explicitly deferred by A1.10.

This opens `WSA-2026-051`.

## 11. WSA-2026-051 - Connections DNS rebinding can bypass private-network containment at the credential-bearing fetch edge

**Severity:** HIGH  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** SSRF / DNS rebinding / credential-bearing provider edge  
**Affected repo:** `AI-Verse-Connections`

### Evidence

`src/util.js`:

- performs one standalone `dns.lookup` for private-network screening.

`src/http.js`:

- after screening, calls ordinary global `fetch(url,...)`.

`src/providers/generic-api.js` and `src/providers/mcp.js`:

- resolve credential handles;
- attach trusted Authorization/header credentials;
- then invoke the shared bounded fetch path.

No address pinning or post-connect address verification exists.

No DNS-rebinding regression test was found.

### Impact

A malicious or compromised external hostname can potentially turn an admitted public-origin connection into:

- private/internal network SSRF;
- bearer/header credential disclosure to a private target;
- access to loopback/link-local/internal service surfaces otherwise blocked by Connections policy.

This is materially stronger than a simple availability defect.

Connections is not in the current Agent release, but it is a frozen standalone public-beta component and would be security-critical for future Full admission.

### Required closure evidence

- resolve the target once under policy and pin outbound connection to one approved IP, or use an equivalent resolver/dispatcher that cannot re-resolve outside the admitted set;
- validate IPv4/IPv6 answers and normalized hostname/origin;
- preserve TLS hostname/SNI verification against the registered hostname;
- reject connected remote addresses outside the approved set;
- apply the same defense to Generic API and MCP;
- add deterministic DNS-rebinding tests where first lookup is public and fetch-time resolution is private;
- prove credentials are never sent on the rebound connection.

## 13. Connections raw-path normalization result

A4.1 rechecks the already-proven Generic API path issue.

Because caller path admission occurs before WHATWG normalization, a path such as encoded dot-segments can normalize outside the allowed prefix while remaining on the same origin.

That is already exactly `WSA-2026-033`.

DNS rebinding is distinct because it changes the network destination after origin/private-network admission and can defeat origin-adjacent network containment even when the pathname is otherwise valid.

## 14. Secret persistence negative space

No new raw-secret-at-rest finding is opened.

- Gateway stores hashed bearer verifiers, not bearer plaintext;
- Gateway config stores provider env-var names, not provider values;
- Brain vendor config rejects credential-bearing flags;
- Memory rejects secret-like learning candidates and is not a secret manager;
- Connections registry/receipts avoid raw vault secrets;
- Token transport/projections avoid raw secret persistence;
- Distribution support bundles sanitize common secret-shaped values.
