## 3. Current public-beta scale boundary

The current supported product is single-operator local/VPS software, not a multi-tenant SaaS fleet.

A4.5 therefore does not require internet-scale throughput.

It does require that normal supported long-lived use does not contain obviously unbounded hot-path algorithms where:

- state grows monotonically under ordinary use; and
- every future request must reread/rewrite all prior state; or
- a normal recurring feature guarantees indefinite growth without an indexed/bounded lookup path.

No formal production SLO is inferred where none is claimed.

## 4. Gateway request/input bounds are strong

Gateway currently bounds important per-request dimensions:

- HTTP request body is capped by configured `max_body_bytes`, default 256 KiB;
- chat messages are restricted to 1..200 items;
- client wait timeout is clamped;
- goal continuation turns are bounded;
- action budgets are bounded;
- request rate limiting exists after authentication;
- Context Ladder hard/soft pressure controls bound runtime invocation context;
- fold archive retrieval has explicit hit/card/message/raw-byte budgets;
- J1 Context Ladder acceptance includes a large-history scenario.

These controls prevent a single ordinary request from becoming an unbounded prompt/context allocation.

Pre-auth CPU exhaustion remains separately tracked as `WSA-2026-050`.

## 5. Gateway Context Ladder / Memory history scale

Gateway Context Ladder does not simply replay all historical text into the runtime.

The reviewed benchmark exercises:

- a 30-run historical fixture;
- old-fact exact recovery;
- fold compaction;
- raw-tail preservation;
- bounded exact source reads;
- bounded fold archive search.

Memory normal recall similarly uses:

- an FTS candidate ceiling;
- a fallback candidate ceiling;

No new Context Ladder/Memory result-size finding is opened.

A4.5 does not interpret the modest benchmark fixture as proof of arbitrary-scale performance; it proves that the intended bounded architecture exists.

## 6. New attack: Gateway idempotency history grows forever in one whole-file JSON object

Gateway owns:

`state/idempotency.json`

with shape:

`{ schema_version, records: { ... } }`.

For every idempotent operation, `claimIdempotency()`:

1. reads and parses the complete JSON file;
2. hashes the current request;
3. inserts one new key;
4. rewrites the complete JSON file atomically.

`commitIdempotency()` then:

1. reads/parses the complete file again;
2. modifies the matching record;
3. rewrites the complete file again.

There is no reviewed:

- record-count cap;
- size cap;
- retention horizon;
- pruning protocol;
- indexed storage;
- shard/segment model;
- replay-window compaction.

## 7. Recurring Automations guarantee normal Gateway idempotency growth

The Gateway Automation wake endpoint always calls:

`claimIdempotency("automation_wake", wake.invocation_id, wake)`.

Automations generates one deterministic, unique invocation ID for each scheduled occurrence.

The supported minimum interval is 60 seconds.

A single always-on one-minute recurring Automation can therefore create up to approximately:

- 1,440 new Gateway idempotency records per day;
- 525,600 per year;

before counting:

- ordinary client idempotency keys;
- control-operation keys;
- additional Automations.

Each newly accepted wake can cause multiple full-file reads/writes whose cost grows with all historical keys.

This is not a synthetic hostile payload; it is a composition of two supported current product features.

## 8. Gateway restart/recovery also performs whole-run-directory scans

Gateway recovery helpers enumerate every run JSON file and individually parse them to locate:

- interrupted runs;
- pending/retryable Memory digests;
- pending organization review;
- scheduled fold work.

This is less severe than the idempotency hot path because it is restart/recovery work rather than every normal request.

It strengthens the conclusion that long-lived run state currently has no indexed operational catalog for some recovery queries.

The stable finding is assigned to the continuously hot idempotency path.

## 9. WSA-2026-058 - Gateway idempotency state has unbounded whole-file growth on supported recurring paths

**Severity:** MEDIUM  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** long-lived runtime state scale / idempotency indexing  
**Affected repo:** `AI-Verse-Gateway`  
**Affected journeys:** recurring Automation wake; idempotent run/control requests; long-lived Gateway operation

### Summary

Gateway stores every idempotency record forever in one JSON object.

Every claim and commit reads/parses and rewrites the entire object.

Supported recurring Automations create a unique invocation ID on every occurrence, so normal 24/7 operation produces monotonic idempotency growth.

### Evidence

`src/paths.mjs`:
- one `state/idempotency.json` path.

`src/store.mjs`:
- `claimIdempotency` reads the whole JSON file;
- inserts a record;
- rewrites the whole file;
- `commitIdempotency` rereads and rewrites the whole file;
- no bounded retention/index is present.

`src/server.mjs`:
- every Automation wake uses `wake.invocation_id` as the Gateway idempotency key;
- run-control idempotency records use the same global store.

Automations:
- scheduled invocation identity is unique per occurrence;
- interval triggers allow a 60-second minimum cadence.

No Gateway long-duration/idempotency-store scale benchmark or retention regression was found.

### Impact

Over long-lived recurring use:

- idempotency request latency becomes proportional to total lifetime keys;
- each new record causes increasing write amplification;
- memory required to parse the state file grows with lifetime history;
- a very large file increases failure/recovery blast radius;
- Automation delivery can be degraded even when each individual wake is small and valid.

The problem is availability/performance rather than a direct authority or data-loss violation, so severity is MEDIUM.

### Required closure evidence

After repair authorization:

1. replace the global whole-file hot-path map with an indexed transactional store or equivalent bounded lookup design;
2. define an explicit replay-retention horizon where records may expire, if expiry is safe;
3. preserve changed-payload rejection and existing idempotency semantics;
4. ensure recurring Automation invocation IDs remain replay-safe;
5. make cleanup/compaction crash-safe;
6. benchmark realistic long-lived key counts, including at least 100k+ records;
7. prove lookup/claim/commit cost does not scale linearly with all lifetime records;
8. re-run Gateway/Automation replay acceptance.

## 10. New attack: Connections reparses lifetime receipts on every external execution

Connections stores execution evidence as one append-only:

`receipts.ndjson`.

`readReceipts()`:

1. reads the complete file into one string;
2. splits every line;
3. parses every receipt into memory.

Every external execution invokes `readReceipts()` before the provider edge to calculate call budgets.

When an idempotency key is supplied, the execution path reads the complete receipt log again under the write lock to find the latest matching key.

Terminal success can perform another lifetime scan through `findIdempotentReceipt()`.

There is no reviewed:

- indexed receipt lookup;
- rolling per-connection budget counter;
- time-partitioned receipt store;
- retained-window index;
- read pagination for the hot execution path;
- receipt-count/size cap.

## 11. Connections normal lifetime growth is material even with call budgets

Default per-connection execution limits include:

- 30 calls/minute;
- 1,000 calls/day.

The daily budget restricts request rate but does not bound lifetime history.

At the default maximum, one connection can produce hundreds of thousands of attempted-external receipts per year.

Idempotent operations can append both reservation and terminal state records.

Every later request still pays the cost of parsing historical receipts that are too old to affect the one-minute or one-day budget.

This is therefore a structural scale defect rather than a missing rate limiter.

## 12. Existing Connections findings amplify the scale cost but remain distinct

A4.3 already opened:

- `WSA-2026-054`: crashed state lock;
- `WSA-2026-055`: permanent pending crash uncertainty;
- `WSA-2026-056`: receipt corruption can disable execution.

A4.4 opened:

- `WSA-2026-057`: provider errors can leak into receipt/CLI diagnostics.

A4.5 does not duplicate them.

The new defect is specifically that *valid, non-corrupt, ordinary lifetime growth* makes every execution increasingly expensive.

## 13. WSA-2026-059 - Connections performs unbounded lifetime receipt scans on every external execution

**Severity:** MEDIUM  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** external-effect history scale / receipt indexing / budget lookup  
**Affected repo:** `AI-Verse-Connections`  
**Affected journeys:** all Generic API/MCP execution; idempotency; rate/daily budget enforcement

### Summary

Connections keeps one lifetime append-only receipt log and reparses the complete log for every external execution.

Current one-minute/day budget checks need only recent per-connection evidence, yet the implementation repeatedly scans all historical receipts.

Idempotency lookup repeats the full scan.

### Evidence

`src/state-store.js`:
- `readReceipts` uses `readFile(..., "utf8")`, split, and JSON parse over all lines;
- `findIdempotentReceipt` calls `readReceipts` then scans the returned array;
- no retention/index/partition is present.

`src/service-execute.js`:
- every execute calls `readReceipts` before `assertWithinUsageBudget`;
- idempotent execute calls another full read under the state lock;
- successful terminal receipt dedupe can trigger another full read.

`src/policy.js`:
- budget enforcement filters the entire supplied receipt array for connection and age.

`src/constants.js`:
- current default daily call budget is 1,000 per connection.

No long-duration receipt-store performance test was found; current limits tests exercise only a tiny history.

### Impact

As receipts accumulate:

- every provider execution incurs increasing disk read, parse, allocation and filter cost;
- idempotent execution can multiply that cost within one request;
- old receipts that cannot affect current minute/day budgets remain in the hot path forever;
- a large valid receipt file can cause latency/memory pressure without any corruption or attack.

Severity is MEDIUM because the failure is gradual availability/performance degradation and not a direct authorization bypass.

### Required closure evidence

After repair authorization:

1. move hot idempotency/budget lookup to indexed state;
2. keep immutable/auditable historical receipts without reparsing all history for each effect;
3. use indexed recent-window queries or durable rolling budget counters with authoritative reconciliation;
4. define compaction/partition/archival rules without losing receipt provenance;
5. preserve exact same-key replay semantics;
6. benchmark at realistic long-lived receipt counts, including 100k+ records;
7. prove bounded execution lookup latency and memory use;
8. re-run corruption, crash-recovery, budget and idempotency tests.

## 14. Automations scale review

Automations uses SQLite with indexes for:

- due triggers;
- retryable runs;
- automation run history.

Per-wake/event bodies are bounded.

Retry attempts are bounded.

Missed interval/cron occurrences are coalesced rather than replaying every missed occurrence after downtime.

One remaining negative-space concern exists:

`_claim_due()` selects every currently due active trigger and claims them inside one `BEGIN IMMEDIATE` transaction without an explicit batch limit.

There is also no global Automation/trigger-count quota.

A very large number of simultaneously due definitions could therefore create a long write transaction and burst of sequential deliveries.

A4.5 does **not** open a stable finding because:

- missed occurrences are explicitly coalesced;
- the current product is single-operator;
- no high-scale trigger-count promise/SLO exists;
- no deterministic evidence establishes a realistic current-beta threshold where this becomes a material failure.

This remains negative-space evidence for future scale hardening.

## 15. Multiple Bots scale review

Multiple Bots uses SQLite and bounded event-page reads.

Current event/timeline endpoints cap page sizes.

Execution queue/recovery operations use indexed state.

However several Dashboard/observability projections intentionally compute a full workspace snapshot by loading all canonical:

- tasks;
- Bots;
- Team Runs;
- Workers/Rooms/Approvals where applicable.

The projection can therefore become O(total workspace history) and some summaries perform per-task lookups.

This is a genuine future scale concern.

A4.5 does not open a new finding because the current public-beta target is single-operator/local and no large-fleet/task-count SLO is claimed.

A5/A6 should not represent this as proven high-scale readiness.

## 16. Data scale review

Canonical corruption is quarantined rather than causing an automatic destructive rebuild.

A4.5 found no new unbounded result-return path in the reviewed normal Data query surface.

Natural-key concurrency remains `WSA-2026-053`, not a scale finding.
