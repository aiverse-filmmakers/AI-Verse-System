## 12. New race: semantic migration source-level replay is not atomic

OS semantic migration explicitly states that source identity is stronger than harmless classifier-plan variation.

Sequential behavior implements that rule:

1. hash source;
2. hash plan;
3. derive `import_key = hash(source + plan)`;
4. check exact import receipt;
5. when no clarification resolutions are present, scan existing migration receipts for the same source hash;
6. if a prior source receipt exists, replay it instead of executing the new plan.

However the first durable migration receipt is written only **after** all owner subactions complete.

There is no source-level reservation/lock before owner effects.

### Concurrent attack

Two simultaneous first imports use:

- the same source text;
- two different valid classifier plans.

Both can execute this sequence:

1. exact `receipt_path` absent;
2. no prior same-source receipt found;
3. continue as fresh imports.

Their `import_key` values differ because the plan digests differ.

All migration owner subaction idempotency keys include that plan-dependent import key, for example:

- `migration:<import_key>:profile`;
- `migration:<import_key>:workspace:<n>`;
- `migration:<import_key>:memory:<n>`;
- `migration:<import_key>:data:<n>`.

Therefore owner-level idempotency does **not** collapse the two classifier plans.

Both can mutate canonical owners.

Both then write different receipts for the same source.

This defeats the documented source-level replay invariant precisely under concurrent first import.

## 13. WSA-2026-052 - concurrent semantic migration can execute multiple classifier plans for one source

**Severity:** HIGH  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** migration concurrency / source-level idempotency  
**Affected repos:** `AI-Verse-OS`  
**Affected journey:** semantic prior-assistant/context migration

### Summary

Semantic migration treats source identity as stronger than classifier-plan variation, but same-source admission is a read/check followed by owner effects followed by late receipt publication.

Two simultaneous first imports of the same source with different plans can both pass the no-prior-source check.

Because subaction idempotency keys are derived from the plan-dependent import key, both plans can execute canonical owner writes.

### Evidence

`scripts/ai_verse_host_adapter.py`:

- exact receipt check occurs before effects;
- same-source receipt scan occurs before effects;
- owner effects execute next;
- final migration receipt is atomically written only after effects;
- subaction keys are derived from `import_key = hash(source_digest + plan_digest)`.

`scripts/test-migration-import.py` verifies:

- exact sequential replay;
- sequential same-source reclassified-plan replay.

No concurrent first-import test is present.

### Impact

One imported context source can concurrently create divergent or duplicate:

- operator profile updates;
- workspaces;
- Memory facts;
- Data candidates;

even though sequential semantics explicitly promise same-source replay rather than re-execution.

This can make migration outcomes depend on scheduling/classifier timing and undermine canonical routing truth.

### Required closure evidence

After repair authorization:

1. reserve/serialize migration admission by source identity before owner effects;
2. make the same-source reservation durable across processes;
3. bind plan choice/result to that reservation;
4. ensure concurrent reclassified plans replay/await the first committed source import rather than execute;
5. define recovery for a crashed in-progress source reservation;
6. add deterministic concurrent same-source/same-plan and same-source/different-plan tests;
7. prove no duplicate/divergent owner writes occur.

## 14. New race: automatic Data natural-key admission is query-then-create

OS automatic structured-current-truth routing does:

1. Brain admits a bounded Data candidate;
2. ensure the Data structure;
3. query Data for the natural-key match;
4. if zero rows exist, call `data.record.create`.

If two different admitted candidates represent the same logical natural key, both can query before either create commits.

Each sees zero rows.

Each then creates.

## 15. Candidate-specific idempotency does not protect natural-key uniqueness

Brain requires a caller-supplied bounded stable `candidate_id`.

It does not derive candidate identity from:

- workspace;
- space;
- entity;
- natural-key field/value.

The OS create idempotency key is derived from candidate ID:

`auto-data:<candidate_id>:record-create`.

Two different candidate IDs for the same:

- workspace;
- space;
- entity;
- match field;
- match value

therefore have different Data idempotency keys.

Data correctly serializes each `record.create` transaction.

But its storage uniqueness is:

`PRIMARY KEY (space_id, entity_id, record_id)`.

Record IDs are independently generated.

There is no storage-level uniqueness constraint for the semantic natural key.

So both transactions can validly commit distinct canonical records with the same intended natural key.

## 16. Resulting failure mode

Once duplicates exist, later automatic structured-truth routing queries with limit 2.

The OS explicitly treats:

- more than one matching canonical row

as:

`ambiguous`

and blocks automatic mutation.

Therefore the race can both:

- create duplicate canonical current truth;
- wedge later automatic updates for that natural key.

This is a canonical data-integrity defect, not only a duplicate UI projection.

## 17. WSA-2026-053 - concurrent automatic Data candidates can create duplicate canonical natural-key records

**Severity:** HIGH  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** structured Data concurrency / natural-key uniqueness  
**Affected repos:** `AI-Verse-OS`, `AI-Verse-Brain`, `AI-Verse-Data`  
**Affected journey:** automatic structured current-truth routing

### Summary

The OS enforces semantic natural-key uniqueness using a query-then-create sequence.

Brain candidate IDs can differ for the same natural key.

Data idempotency is keyed to that candidate-specific create key, and storage uniqueness covers generated record IDs rather than semantic natural keys.

Two concurrent admitted candidates can therefore both observe no match and commit separate canonical records for one logical natural key.

### Evidence

Brain `admit_data_structure_candidate`:

- accepts a bounded caller-supplied `candidate_id`;
- independently accepts `match.field` and `match.value`;
- does not require candidate ID to be derived from that match.

OS `_request_data_structured_truth`:

- performs `data.query`;
- if zero rows, performs `data.record.create`;
- create idempotency key is derived from `candidate_id`.

Data:

- wraps each create in a transaction;
- idempotency key is unique per submitted key;
- creates a generated record ID;
- storage primary key is `space_id, entity_id, record_id`;
- no atomic natural-key uniqueness constraint was found.

No concurrent competing-natural-key test was found in the reviewed OS/Data suites.

### Impact

Concurrent automatic organization can create conflicting duplicate canonical structured truth.

Subsequent automatic routing can become permanently ambiguous for that logical record until manual cleanup/reconciliation.

### Required closure evidence

After repair authorization:

1. move semantic uniqueness admission into the Data owner;
2. define an owner-authoritative unique key/constraint or atomic upsert/CAS contract;
3. do not rely on OS query-before-create for uniqueness;
4. bind idempotency/replay to semantic identity where appropriate;
5. test simultaneous different candidate IDs with the same natural key;
6. prove exactly one canonical record exists;
7. prove same-key differing payload behavior is deterministic and auditable.
