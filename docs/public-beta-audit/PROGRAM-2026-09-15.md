# Independent Whole-System Public-Beta Audit Program

**Date:** 2026-09-15  
**Status:** CANONICAL PRE-DOGFOOD AUDIT PROGRAM  
**Purpose:** independently verify the current AI-Verse system before Mission Control MC1.4 and broader owner dogfood.  
**Methodology authority:** `docs/AUDIT-METHODOLOGY.md`  
**Execution tracker:** `docs/public-beta-audit/EXECUTION-TRACKER-2026-09-15.md`  
**Finding protocol:** `docs/public-beta-audit/EVIDENCE-FINDING-PROTOCOL.md`  
**Relationship protocol:** `docs/public-beta-audit/RELATIONSHIP-MATRIX-PROTOCOL.md`

## 1. Decision

The independent whole-system public-beta audit runs **before** the real Mission Control -> AI-Verse local proof and before owner dogfood.

The audit is not a quick reread of existing System specifications.

It is a fresh evidence program that:

1. reconstructs each repository independently from its own current source;
2. audits every actual or claimed cross-repository seam;
3. audits supported end-to-end product journeys;
4. attacks the system with failure/security/concurrency/negative-space checks;
5. revalidates public-beta acceptance evidence and release claims;
6. synthesizes one whole-system verdict and ordered repair plan.

Dashboard MC1.4 remains paused until this audit reaches its final verdict and any blocking findings are resolved.

## 2. Independence rules

The existing `docs/AUDIT-METHODOLOGY.md` remains authoritative.

For this program, independence additionally means:

- product repositories are **read-only evidence** during audit collection;
- do not fix findings while collecting audit evidence;
- do not use existing AI-Verse-System component specs as evidence during a repository's first-pass standalone reconstruction;
- do not use another repository to fill gaps during standalone reconstruction;
- previous chat summaries are navigation hints only, never evidence;
- current executable implementation outranks prose;
- current tests/CI outrank status claims;
- unresolved contradictions are recorded, not silently reconciled;
- absence must be phrased as "not found in reviewed evidence" unless exhaustively proven;
- every task records exact reviewed SHA(s);
- every task has its own checkpoint/PR in AI-Verse-System.

This prevents the auditor from merely confirming the architecture we already believe exists.

## 5. Snapshot rule

A0 creates an immutable audit snapshot:

- default branch;
- exact head SHA;
- open PRs;
- active release branches/tags where relevant;
- accepted candidate refs;
- latest CI state;
- repository visibility;
- license;
- current intended milestone.

Open PRs are **not** current product truth.

The default audit target is the pinned default-branch SHA.

If a repository changes while the audit is running:

1. record drift;
2. classify whether the change touches already-audited behavior;
3. if material, mark affected audit packets STALE and rerun them against the new accepted snapshot;
4. never silently mix revisions.

## 6. Context-bloat control

The audit is deliberately serial.

### One active task

Only one tracker task may be ACTIVE at a time unless two tasks are mechanically independent and the tracker explicitly allows parallel execution.

### One task, one checkpoint

Every completed task:

- produces a bounded evidence packet;
- records exact refs;
- records findings;
- updates the tracker;
- merges as its own System PR/checkpoint before the next task begins.

### Repository task micro-checkpoints

If a repository audit is too large for one working context, split it at these fixed internal checkpoints without changing scope:

**R-a Reconstruction**
- tree/canonical roots;
- identity/build/license;
- architecture/contracts;
- lifecycle surfaces;
- runtime boundaries.

**R-b Enforcement**
- implementation;
- schemas/validators;
- tests/CI;
- security/isolation;
- history/repair evidence;
- all mandatory audit lenses.

**R-c Verdict**
- contradiction scan;
- negative-space scan;
- lifecycle/completeness matrices;
- findings;
- standalone verdict.

Do not read another product repo between R-a and R-c.

### Cross-task continuity

A future auditor should need only:

1. this program;
2. the execution tracker;
3. the completed evidence packet for the immediately preceding task;
4. current GitHub state.

Conversation history is not required.

## 7. Finding classification

Every material issue receives a stable finding ID.

Severity:

- **BLOCKER**: security, data loss/corruption, authority/isolation breach, unsupported release path represented as supported, install/setup blocker, or systemic flaw that invalidates dogfood.
- **HIGH**: major correctness/reliability/ownership failure with realistic user/system impact.
- **MEDIUM**: meaningful defect or architectural debt that can be bounded/deferred with explicit risk.
- **LOW**: minor defect, docs drift or product roughness without material system risk.
- **INFO**: observation, design note or verified limitation.

Confidence:

- **PROVEN**
- **STRONG**
- **POSSIBLE**
- **UNVERIFIED**

State:

- OPEN
- DUPLICATE
- DEFERRED
- NOT-A-BUG
- FIXED-PENDING-RECHECK
- CLOSED

Dogfood gate:

- all BLOCKER findings must be CLOSED;
- all HIGH findings must be CLOSED unless the owner explicitly accepts a narrowly bounded risk after the final synthesis;
- MEDIUM findings require fix or explicit documented deferment;
- LOW/INFO may remain open if tracked.

## 8. Phase A0 - Scope, snapshot and audit controls

**Goal:** establish exactly what is being audited and freeze the evidence rules.

### A0.1 Product/repository universe
Verify every repo in scope and explicitly list exclusions.

### A0.2 Immutable snapshot
Record exact refs, open PRs, release/candidate refs and CI state.

### A0.3 Evidence/finding ledger
Instantiate finding IDs, evidence references, severity/confidence rules and contradiction register.

### A0.4 Relationship-matrix skeleton
Create the directional all-repo matrix. Every pair is initially UNKNOWN, then classified as REQUIRED, ALLOWED, FORBIDDEN or NONE with relation types.

### A0.5 Freeze gate
Confirm product repos are read-only for audit collection, Dashboard MC1.4 is paused, and A1 is the only active phase.

**Exit:** no ambiguity about scope, revisions, evidence or sequencing.

## 10. Phase A2 - Cross-component relationship audit

**Goal:** verify the whole graph, not just individual parts.

A2 starts by merging all A1 outbound/inbound claims into the relationship matrix.

### A2.1 Relationship matrix resolution
For every directional repo pair, classify:

- REQUIRED;
- ALLOWED;
- FORBIDDEN;
- NONE;
- unresolved.

Relation types include:

- lifecycle/discovery;
- read;
- write;
- command/control;
- event;
- identity/scope;
- permission/approval;
- telemetry/cost;
- release/version;
- credential/effect.

Every REQUIRED or FORBIDDEN relation requires evidence. NONE requires negative-space evidence when the pair is architecturally sensitive.

### A2.2 Canonical ownership and write paths
Trace all canonical owners and every write path.

Specifically search for:

- direct storage writes across owner boundaries;
- duplicate ledgers;
- shadow caches treated as truth;
- Dashboard/Apps/Gateway writing canonical state they do not own;
- Multiple Bots duplicating Token pricing/cost truth;
- Brain or LLM output bypassing security authority.

### A2.3 Lifecycle/discovery/adoption/reconcile graph
Verify:

- install-order behavior;
- discovery;
- attach/register;
- activate/adopt;
- migration/import;
- reconcile;
- disable/detach;
- update/rollback;
- uninstall/reinstall.

### A2.4 Identity, scope, isolation and authentication
Verify:

- system_id;
- workspace_id;
- principal;
- actor;
- Bot/Worker/Room/Thread identities;
- session/run binding;
- cross-system isolation;
- auth principal vs protocol actor text;
- remote client trust.

### A2.5 Read/retrieval/context/data flows
Trace:

- OS/context reads;
- Memory;
- Context Ladder/folds;
- Brain retrieval;
- Skills;
- Data;
- Dashboard/Apps projections;
- provenance and visibility.

### A2.6 Runtime, task, Bot and automation event flows
Trace:

- Gateway runs/sessions/events;
- Bot/Worker task execution;
- Brain decisions;
- automation wake/invoke;
- consent;
- retries;
- restart replay;
- idempotency;
- no-progress/parking/cancel/pause/resume/approval.

### A2.7 Telemetry, Token, cost, audit and receipts
Verify:

- Token remains canonical for normalized usage/pricing/cost truth;
- execution-local counters remain projection/evidence where intended;
- ACTUAL/CALCULATED/UNKNOWN semantics;
- immutable evidence;
- receipts/provenance do not leak hidden resources.

### A2.8 Version, compatibility, release and install-order graph
Verify every supported composition:

- current accepted component refs;
- compatibility contracts;
- Distribution composition;
- old/new mismatch behavior;
- fail-closed unsupported combinations;
- public/member paths match accepted paths.

**Exit:** all meaningful relationships are verified or captured as findings. No UNKNOWN relation may remain if it affects a supported user journey or authority boundary.

## 11. Phase A3 - End-to-end product journey audit

**Goal:** verify the system as a user/runtime experiences it.

Only paths claimed as currently supported at the snapshot are required to pass. Planned paths are labeled planned, not failed.

### A3.1 Clean install and first-use journey
Distribution/package -> install -> discovery -> readiness -> usable current profile.

### A3.2 Existing-system attach/adopt/migration journey
Existing AI-Verse folder/data -> semantic classification -> owner routing -> migration/reconcile -> no data loss.

### A3.3 Gateway chat/run/restart journey
Client -> Gateway -> OS/context/runtime -> run events -> result -> restart/recovery.

### A3.4 Context/Memory journey
Input/history -> Memory/context projection -> Context Ladder/folds -> retrieval -> visibility/provenance -> exact fallback where required.

### A3.5 Goal/self-learning journey
User goal -> Brain strategy/evaluation -> Skill learning/proposal/adoption -> evidence/rollback boundaries.

### A3.6 Multiple Bots/team execution journey
Task -> Bot/Worker/Room/Thread/Team Run -> runtime -> operational budgets -> completion/receipts -> canonical owners preserved.

### A3.7 Automation journey
Request -> consent -> schedule -> trigger -> Gateway/OS execution -> restart replay -> changed-replay rejection -> receipts.

### A3.8 Connection/external-effect journey
Intent -> Connection credential/effect boundary -> approval -> action -> evidence -> failure/retry.

### A3.9 Token/usage/cost journey
Runtime evidence -> normalization -> pricing evidence -> Token truth -> projections -> unknown handling.

### A3.10 Lifecycle/recovery/isolation journey
Update/rollback/disable/uninstall/reinstall + crash/restart + two-system A/B isolation + supported cross-platform path.

Dashboard is observed where it currently participates but incomplete Mission Control work is not treated as a current supported journey.

**Exit:** supported user journeys have evidence end to end, not merely component-local tests.

## 12. Phase A4 - Adversarial and negative-space audit

**Goal:** try to falsify the system's safety and reliability assumptions.

### A4.1 Security/path/secret/remote-boundary attacks
Inspect path traversal, symlink escape, credential leakage, unsafe remote bind, origin/auth checks, plugin/runtime escapes and permission bypass.

### A4.2 Concurrency/idempotency/replay attacks
Inspect duplicate requests, racing workers, retries, restart replay, stale approvals, repeated schedule fire, repeated migration/reconcile and lock behavior.

### A4.3 Partial failure, corruption and recovery attacks
Inspect crashes between writes, partial component availability, stale caches, corrupted state, missing dependencies, rollback, repair and safe degradation.

### A4.4 Privacy/visibility/provenance attacks
Inspect cross-workspace/resource leakage, hidden-resource existence leakage, audit/receipt leakage, memory visibility, logs, diagnostics and exports.

### A4.5 Scale/current-generation/negative-space attacks
Inspect realistic data/task/session growth, unbounded scans, resource exhaustion, current runtime/model/host compatibility, unsupported platform assumptions and missing enforcement hidden behind prose.

**Exit:** no unexamined high-risk negative space remains for the current public-beta profile.

## 13. Phase A5 - Acceptance and release-evidence revalidation

**Goal:** independently challenge every "accepted", "ready", "public beta" or "supported" claim.

### A5.1 Test/CI evidence validation
Check what current CI actually runs and what it does not prove.

### A5.2 Accepted refs and release-candidate validation
Reconstruct accepted component refs, immutable release identity and candidate boundaries.

### A5.3 Documentation/status contradiction scan
Compare README/docs/status trackers/blueprints with current implementation and CI.

### A5.4 Product-path/clean-machine/current-generation validation
Verify accepted paths use the real supported installation/attach/runtime boundary and current generation dependencies rather than internal shortcuts.

**Exit:** release evidence can be trusted as written, or findings explain exactly where it cannot.

## 14. Phase A6 - Whole-system synthesis and verdict

**Goal:** convert evidence into one actionable system truth.

### A6.1 Global contradiction register
Deduplicate contradictions from all phases.

### A6.2 Root-cause/finding graph
Group symptoms under root causes and identify affected repos/seams/journeys.

### A6.3 Whole-system verdict
One of:

- **NO-GO**
- **CONDITIONAL GO**
- **GO FOR CONTROLLED DOGFOOD**

The verdict must be evidence-based, not optimistic.

### A6.4 Ordered repair program
Create the dependency-safe repair sequence:

1. security/data-loss/authority/isolation;
2. lifecycle/install/setup/release blockers;
3. cross-component contract failures;
4. reliability/recovery;
5. medium correctness;
6. documentation/product roughness.

### A6.5 Audit freeze and canonical propagation
Record:

- exact audited snapshot;
- final findings;
- verdict;
- repair order;
- affected System docs;
- what must be rerun after repairs.

Do not rewrite history to make the pre-fix system look clean.

**Exit:** the audit is complete and the repair program can begin.

## 15. Post-audit repair and recheck

Repairs are a separate execution program.

Rules:

- fix one root finding or tightly coupled cluster at a time;
- product repo PRs may begin only after A6;
- each repair names the finding IDs it closes;
- rerun the affected standalone repo checks, seams and journeys;
- a finding closes only after regression evidence;
- any repair that changes a canonical contract triggers downstream re-audit.

After all BLOCKER/HIGH gates are resolved, run a bounded final independent recheck before resuming Dashboard MC1.4 and owner dogfood.

## 17. Stop rules

Immediately pause the audit if:

- a credible active security vulnerability exposes users/secrets;
- a data-loss/corruption path is currently reachable;
- an authority/isolation violation makes further testing unsafe;
- the audited branch/ref changes materially and invalidates the snapshot;
- required evidence is inaccessible.

Record the stop reason before remediation.

## 18. Definition of audit complete

The audit is complete only when:

- repository universe is explicit;
- exact revisions are pinned;
- every scoped repo has an independent packet;
- the relationship matrix is resolved;
- all supported end-to-end journeys are audited;
- adversarial lenses are complete;
- release evidence is revalidated;
- contradictions/findings are deduplicated;
- whole-system verdict exists;
- repair order exists;
- all skipped/unverifiable areas are explicitly listed;
- Dashboard MC1.4 remains blocked or is explicitly released by the final verdict.

Until then, "independent whole-system public-beta audit complete" must not be claimed.
