## 3. Ordinary public product entrypoint

Distribution's README presents the ordinary first run as:

`aiverse start`

The current CLI parser defines `start` as:

> one-action first run using the exact released Agent profile

The CLI dispatches directly to:

`Orchestrator.start(...)`

For a fresh installation, `Orchestrator.start`:

1. resolves an admitted Agent release set;
2. creates the selected root;
3. invokes Distribution `install(profile="agent", ...)`;
4. asks live owner-backed status;
5. invokes owner setup when required;
6. runs composed doctor;
7. refuses success when readiness is not proven;
8. records the first-run evidence;
9. returns the progressive conversational handoff only after doctor succeeds.

The successful product message is:

`AI-Verse is ready. What would you like help with?`

A5.4 therefore does **not** find a “release gate bypasses `aiverse start`” defect.

- `json-subprocess`.

The `openai-compatible` implementation performs a real HTTP `fetch` to:

`<base_url>/v1/chat/completions`

and handles:

- model selection;
- messages;

- max output tokens;
- bearer credential from the configured environment-variable name;
- response content/tool-call mapping;

Gateway local tests do exercise `json-subprocess` through server paths.

Current test inventory found no `setupComponent(... runtime: "openai-compatible" ...)` product test and no direct `RuntimeRegistry` openai-compatible invocation test.

Some loop-contract tests attach `kind: "openai-compatible"` metadata when validating worker/automation authority binding, but they do not drive the actual upstream network adapter.

Even if a local Gateway test were added, A5.4 would still require the **composed immutable Distribution product path** to prove its supported runtime edge.

## 13. WSA-2026-063 - Agent clean-machine release evidence substitutes Gateway's deterministic test runtime for the supported runtime edge

**Severity:** MEDIUM  
**Confidence:** PROVEN  
**State:** OPEN  
**Root area:** product runtime release evidence / supported runtime boundary  
**Affected repos:** `AI-Verse-Gateway`, `ai-verse-distribution`

### Summary

Distribution's clean-machine Agent release gate uses the real `aiverse start` path and real Gateway HTTP API, but configures Gateway with the deterministic zero-network runtime that Gateway itself labels for local testing.

No reviewed default/candidate clean-machine Agent acceptance drives the documented non-test runtime edge such as `openai-compatible`.

### Why this is not a runtime implementation failure

The openai-compatible adapter exists.

A5.4 does not prove it is broken.

The finding is that the release evidence used to certify the member product path stops one boundary before the real selected runtime/provider edge.

### Impact

A release can pass while defects remain undetected in product-path behavior such as:

- upstream runtime URL handling;
- bearer injection from `api_key_env`;
- model propagation;
- tool-call request/response translation;
- usage mapping;
- provider timeout/failure propagation;
- real runtime readiness under an immutable Agent installation;
- interaction between clean-machine Distribution setup and non-test Gateway runtime configuration.

This weakens the statement that the clean-machine gate proves the complete supported product execution path.

### Required closure evidence

After repair authorization, add immutable composed acceptance that:

1. begins from `aiverse start` on a fresh Distribution root;
2. uses an admitted exact Agent release/candidate;
3. configures Gateway through the supported non-test runtime boundary;
4. drives the actual `openai-compatible` network adapter, using a protocol-faithful local mock upstream if an external provider would make CI nondeterministic;
5. verifies the configured model is sent;
6. verifies environment-backed bearer injection without persisting/exposing the secret;
7. verifies normal content and tool-call response mapping;
8. verifies token/usage fields;
9. verifies upstream HTTP failure and timeout behavior;
10. verifies Gateway restart does not change runtime binding unexpectedly;
11. proves the same path on Ubuntu, macOS and Windows;
12. retains deterministic-runtime acceptance as supplemental deterministic coverage, not the sole composed runtime proof.

A real external paid provider is not required if the acceptance exercises the actual network adapter and its complete protocol/security boundary deterministically.
