## 20. Mechanical anti-repointing limitation

The release-set contract says every released set has:

- a stable release-set ID;
- exact immutable component revisions.

Catalog validation verifies:

- IDs;
- statuses;
- profiles;
- full 40-character SHAs;
- repository URLs;
- dependency-lock structure;
- channels;
- compatibility references.

Mirror tests ensure public/runtime catalog equality.

However A5.2 found no repository test that compares an already accepted release-set ID to historical Git state and rejects future repointing of that same ID.

This means immutable component refs are mechanically enforced, while long-term “same release ID must never change its component map” currently relies on release governance/Git review.

A5.2 does **not** open a current defect for this negative space because:

- all finalized Agent manifests are empirically unchanged after their final PR heads;
- Git history preserves previous identities;
- current installation resolves the expected composition;
- no silent repoint has occurred.

A later release-train hardening should make this contract invariant executable.

- profile;
- status.

- public compatibility == runtime compatibility;
- public release manifests == runtime release catalog.

Therefore all mirrors can consistently preserve the same stale compatibility blocker while CI remains green.

`Catalog.resolve("full")` raises `ReleaseBlockedError` using the blockers from the release-set record, not the stale compatibility blocker list.

So current install selection still fails closed for the correct remaining Full blocker.

The defect is machine release/status truth, not install admission.
