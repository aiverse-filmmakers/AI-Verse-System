## 3. Distribution audit

### 3.1 Shipped update semantics

Current Distribution CLI behavior matches completed Core Update Program v1:

- plain `aiverse update` calls the mutating safe updater;
- `aiverse update --plan` is the read-only preview;
- the hidden legacy `--apply` compatibility flag does not redefine normal member semantics and cannot be combined with `--plan`;
- current CLI has `status`, `doctor` and software `rollback` surfaces;
- current CLI does not yet expose product-level `upgrade`, `upgrade --apply`, `restore`, or `restore --apply` surfaces.

**Classification:** `REUSE/EXTEND`. Do not create a second updater.

### 3.2 Update transaction and fail-closed behavior

`src/aiverse_distribution/core_update.py`, `core_update_guard.py`, `update_safety.py`, `update_journal.py`, `state.py`, `core_update_health.py` and `generated_refresh.py` already provide reusable update infrastructure:

- exact release/component selection;
- source-clean and ownership guards;
- refusal on ambiguous, dirty, symlinked or untrusted changed sources;
- serialized lifecycle mutation;
- pending owner-effect markers and exact resume requirements;
- persistent Core update journal;
- pre-mutation Distribution receipt checkpoint;
- staging of exact component revisions;
- owner migration and reconcile for changed owners;
- receipt-bound generated-file replacement and bounded byte restoration;
- mandatory final `status` plus `doctor` health gates;
- software/receipt rollback after failed health;
- interrupted-update recovery that either verifies/finalizes the intended target or rolls software state back when safe;
- explicit refusal to pretend owner-state rollback succeeded when owner mutation is not rollback-safe.

The journal deliberately stores software receipts/lifecycle metadata, not canonical user/owner state. Generated-file restoration is also limited to files proven Distribution-generated by receipt/digest.

**Classification:** transaction engine `REUSE/EXTEND`; zero-loss ownership guard `REUSE`; whole-install recovery `CREATE` on top of these primitives.

### 3.3 Release-set and activation evidence

`release_catalog.py` and `transition_contract.py` already enforce:

- exact 40-character component commit SHAs;
- released/blocked/retired release status;
- channels resolving only to admitted released sets;
- forward Core lineage;
- explicit evidence-bound directional update/rollback transitions;
- transition compatibility checks;
- `owner-preserved` state rule;
- `software-only-owner-state-preserved` rollback rule;
- accepted qualification evidence bound to the exact from/to transition;
- safe refusal of unsupported transitions.

**Classification:** `REUSE/EXTEND` for structural compatibility/admission metadata. Do not build a parallel release-selection framework.

### 3.4 One-command doctor substrate

Distribution `Orchestrator.doctor()` already fans out owner doctor surfaces sequentially for installed profile components, preserves isolated per-owner results, continues other safe checks after an owner exception, runs the composed project doctor, and prevents one failed owner from becoming a false aggregate PASS.

Existing adapters already route to owner checks, including OS doctor and Skills doctor.

**Classification:** `REUSE/EXTEND`. The missing work is infrastructure/convergence findings and simpler member-facing aggregation, not a new doctor framework.

### 3.5 Natural-language routing

Distribution `AGENTS.md` and `CLAUDE.md` already establish preservation-safe natural-language update routing:

- completed installs route to lifecycle update rather than reinstall/delete/reset/reclone;
- ordinary update means `aiverse update`;
- release IDs and internal component revisions stay hidden unless explicitly requested;
- update conflicts preserve files and fail closed;
- success is not reported before canonical lifecycle health passes.

OS has a dedicated update-request contract verifier and CI workflow for natural-language update routing.

Current audited instructions do not yet define equivalent complete natural-language routing for doctor, structural upgrade, or restore.

**Classification:** update routing `REUSE/EXTEND`; doctor/upgrade/restore conversational routing `EXTEND/CREATE` within the same lifecycle contract.

## 4. OS audit

### 4.1 Workspace identity and current layout

Current OS workspace manifests already provide stable logical identity through `WORKSPACE.yaml` schema `2.0` and an explicit `id` field. `scripts/workspace-owner.mjs` can rediscover a workspace by directory name, manifest ID or normalized name, and performs conservative additive evolution without rewriting unsupported/custom YAML shapes.

However, current canonical creation still materializes a workspace directly as:

`workspaces/<workspace-id>`

The current workspace README also documents this flat layout. There is no current admitted domain-first hierarchy migration in that owner path.

The motivating workspace problem is therefore **reproduced/classified from the live implementation**: stable identity exists, but current creation still reproduces the flat path structure and there is no owner migration for the proposed hierarchy class.

**Classification:** stable workspace identity `REUSE`; conservative workspace owner `REUSE/EXTEND`; hierarchy semantics `EXTEND`; hierarchy migration/reference repair `CREATE` under OS ownership once Phase 1 freezes the target architecture.

### 4.2 Existing migration patterns

OS `scripts/migration-import.py` provides an authorized, idempotent and reversible import/migration pattern for context/memory migration drops. It is not a workspace hierarchy migration.

**Classification:** migration safety pattern `REUSE`; workspace hierarchy recipe/handler still `CREATE` after architecture is frozen.

### 4.3 OS health surfaces

OS already exposes:

- `ai-verse-os status`;
- `ai-verse-os doctor`;
- composed component status/doctor;
- `scripts/check-architecture.sh`.

The OS doctor covers structural, setup, attachment/discovery, runtime, dependency and system-composed health. It explicitly does not claim owner-specific operational checks it does not own. `check-architecture.sh` verifies canonical architecture files, workspace template invariants, capability source consistency, runtime adapter synchronization, and warns about tracked user-owned state.

**Classification:** `REUSE/EXTEND` as an owner health surface for Distribution aggregation.

### 4.4 Generated/member-facing projections

Built-in OS capabilities are canonically sourced under `system/capabilities/` and projected to `.agents/skills/` and `.claude/skills/`. The architecture checker verifies byte-level synchronization of those projections.

Any later structural migration affecting referenced capability paths must therefore treat these generated projections as an explicit verification/reference-repair surface.

## 5. Skills audit

### 5.1 Existing immutable lifecycle

Skills already has a mature managed-distribution lifecycle:

- canonical managed root under `~/.aiverse/skills`;
- immutable generations;
- atomic `active.json` activation pointer;
- generation manifests, content digests and provenance;
- exact execution pinning and leases;
- serialized lifecycle mutations;
- safe rollback by pointer change;
- uninstall without deleting retained generation bytes;
- legacy mutable schema-2 migration into a verified retained generation;
- adapter manifests bound to exact generation and digest;
- stale adapter detection.

**Classification:** `REUSE/EXTEND`. Do not create another Skills package lifecycle.

### 5.2 Stable package identity/provenance and missing scope field

Current Skills manifest/registry machinery provides stable package IDs and provenance. The audited skill schema and central registry do not expose a canonical workspace/domain/OS-wide scope field.

This proves that the motivating reusable-Skill problem is not caused by a missing package generation system. It is a provider/scope-placement problem.

### 5.3 Material ownership conflict discovered

The current Safe Infrastructure plan says Skills owns Skills scope semantics and safe promotion/re-scoping migrations.

The live shipped cross-repo contracts say otherwise:

- `AI-Verse-Skills/docs/AI_VERSE_OS_INTEGRATION.md` says Skills owns distributed package lifecycle, while OS owns scope/provider resolution, permissions, connections and execution routing.
- `AI-Verse-OS/system/contracts/capability-provider-v1/README.md` defines distributed Skills as one provider while personal reusable Skills and active-workspace Skills are distinct providers with OS-owned resolution/ranking semantics.
- personal reusable packages are user-owned rather than installer-managed Skills distribution state;
- workspace Skills remain workspace-owned rather than installer-managed distribution state.

This is a protected canonical-ownership conflict. It cannot be silently resolved as a task-level implementation choice.

**Classification:** planned Skills-owned cross-provider scope/re-scoping direction `BLOCKED - PLAN AMENDMENT REQUIRED` before implementation. Skills package lifecycle remains `REUSE/EXTEND`.

## 6. Recovery and restore reality

The current system has several important but bounded recovery mechanisms:

- Distribution software receipt/journal rollback for failed/interrupted Core update transactions;
- Distribution digest-bound restoration of its own generated files;
- owner-native transactional behavior;
- Skills immutable generation rollback;
- OS preservation of ignored canonical user state across its own update/reinstall path.

These mechanisms do **not** currently provide the product guarantee defined by this program:

- there is no one rotating whole-local-installation Last-Known-Good representation;
- there is no current `aiverse restore` preview surface;
- there is no current `aiverse restore --apply` whole-install restore transaction;
- current Distribution Core rollback is explicitly software-only and owner-state-preserving, not a rewind of covered local owner/user state;
- the Core update journal explicitly does not capture canonical owner/user state.

**Classification:** existing owner/update recovery `REUSE/EXTEND`; whole-install Last-Known-Good rotation and restore preview/apply `CREATE` on top of the existing transaction/verification substrate.

The exact future recovery coverage for large assets/media/outputs, credentials/secrets, reconstructible tool/dependency state, disposable caches and external side effects is intentionally not guessed in Slice 1.1. It remains a Phase 1 inventory/freeze decision after the ownership amendment is resolved.

## 11. PLAN AMENDMENT PROPOSED

### Current protected assumption

The current plan states that Skills owns Skills scope semantics, workspace/domain/OS-wide scope decisions and safe promotion/re-scoping migrations.

### Evidence requiring amendment

Current shipped cross-repo contracts assign:

- Skills ownership to distributed package lifecycle, package metadata/provenance and immutable generations;
- OS ownership to provider scope, provider resolution/ranking, permissions and execution routing;
- personal reusable Skills to a separate user-owned provider;
- workspace Skills to workspace-owned state rather than the installer-managed Skills distribution.

### Proposed ownership correction

Preserve the product outcome while aligning implementation ownership with shipped contracts:

- OS owns cross-provider Skill scope semantics/resolution and the mapping from practical member intent such as "use everywhere", "all YouTube work", or "only this project" into canonical provider/scope placement.
- Skills owns the managed distributed provider's package lifecycle, stable package identity, package provenance, immutable generations, validation and any migration wholly internal to that provider.
- Promotion/re-scoping that moves user/workspace Skills across providers is an OS-owned structural migration, using Skills validation/provenance primitives where appropriate, not a Skills-owned filesystem-placement decision.
- Distribution continues to coordinate admitted owner migrations without inventing either domain's semantics.

### Affected plan surfaces

At minimum:

- permanent law 1.6;
- Intended ownership / AI-Verse-Skills;
- Slice 1.2 ownership inventory;
- Slice 1.3 architecture freeze;
- Slice 2.2 recipe ownership;
- Slices 3.3 and 3.4;
- downstream Distribution orchestration and Phase 5 tests referring to the Skill scope owner.

### Acceptance-floor effect

No member-facing safety or capability outcome needs to weaken. The amendment changes canonical ownership and recipe placement so implementation matches existing architecture. User-owned preservation, stable identity/provenance, explicit migration, reference repair, practical-language UX and deterministic convergence requirements remain intact.

### Resume rule

Do not begin the affected Slice 1.2 ownership freeze or any Skill scope/re-scoping implementation until this amendment is resolved in the canonical plan.
